# Dev Lab

## Status

Stack 1.0 (16 May 2026): Fully playable. Snake of colored dots approaches player; player shoots matching bullets to remove the leading dot (wrong colors add a dot). Bullets have a fading trail, correct hits trigger a dot explosion with alpha fade. Levels increase dot count and snake speed. Gap narrowing with level is not yet implemented.

Slots 1.0 (17 May 2026): Fully playable. Three wheels with fruit symbols spin on button press, each with random speed and duration; jackpot win when all three match. Cylinder brightness gradient and click sounds during spin.

SimonSays 1.0 (17 May 2026): Fully playable. Player repeats an ever‑growing color‑and‑tone sequence; a wrong answer restarts the current level. The game spans 120 levels — conquering the full strip triggers the victory ending.

Race 1.0 (17 May 2026): Fully playable. Two players, each controlled by a single button; boosting accelerates their racer while friction gradually slows them down. Bouncing off strip ends, laps counted by total distance travelled. Colored progress bars grow from each player's side toward the centre; first to reach the finish line wins.

Darts 1.0 (6 Nov 2026): Fully playable. A needle sweeps continuously across a four-ring target; one press arms the sweep, a second freezes it and scores whichever ring it lands on. Fixed 48 darts across 12 levels, with needle speed and target size both easing from gentle to punishing as levels climb. One progress bar tracks darts thrown, the other shows score as a fraction of the maximum, changing color through four ranks as it climbs — no lives or retries, just how high a score you reach before the darts run out.

FlappyBird: Bird falls with gravity, one button boosts upward; top and bottom terrain walls move randomly with shrinking gap and increasing fluctuation/speed.

Pacman: Player moves bidirectionally along linear strip using two buttons; collects regular and power pellets that temporarily change player state; progresses through 10 levels with increasing power pellet density.

Moodlight: Shows continuous rainbow gradient; three buttons control speed (increase, decrease, reset).

#### [22 Nov 2026 – Claude Sonnet 5 – DemoScene synced to a real track, a loop-wrap audio bug fixed, and the audio engine's own sense of time corrected](log/20261122.md)

`DemoScene` given its own `Tracker`, loading `faggots_universe.mod` the same way `Test.js` does; time-based stage cycling (`STAGE_DURATIONS`, ten `Stage`s each held a fixed number of seconds) replaced with cycling driven by `tracker.segment` directly, since the file's 27 segments are each exactly one bar (64 rows) — no need for `tracker.bar`. Decision: loop only the first 24 segments (`tracker.play(0, 0, 24, true)`), skip the outro. Stage slot = `Math.floor(tracker.segment / BARS_PER_SLOT) % stageCount`. Six of ten existing `Stage`s kept (`FIREWORKS`, `AURORA_BOREALIS`, `COPPER_BARS`, `SCANNER`, `REACTIVE_BURST`, `BOUNCING_BALLS`), four dropped from the cycle (`FRACTAL_MOUNTAIN`, `STARFIELD_WARP`, `DIGITAL_RAIN` judged weak individually; `INTERFERENCE` dropped last as the most generic-plasma-looking once `SCANNER`/`COPPER_BARS` already covered similar moving-bar ground with more craft) — no dropped stage's code touched or removed, only excluded from the active cycling list. `BARS_PER_SLOT` corrected from an initial `4` to `2` (six-stage cycle runs twice per 24-bar loop, not once).

Real bug found in the worklet's `Tracker`: looping (`loop: true`) was new territory (`Test.js` only ever used `loop: false`), and whatever was still sounding at the tail of the loop range kept ringing straight through the wrap into the next pass instead of cutting cleanly. Root cause (found by checking the position/segment/bar math numerically first, which was correct) — `Tracker.active[]` (deliberately never cleared between ordinary bars, "a bar with nothing new in it doesn't mean silence") was never cleared specifically at the loop seam either. Fixed by tracking which full pass the playhead is on (`cycle = floor(position / totalDuration)`) and clearing `active` the instant that number changes, same mechanism `play()`/`stop()` already use, just automatic on wrap. (A further, smaller artifact was noticed right at the loop's end after this fix and explicitly set aside unexamined — "just to prove the point.")

Source-agnostic `Analyzer` designed (not built): `process(sample)` streaming interface, `level` (0–1, RMS/peak with one-pole smoothing, O(1) state) trivial on an MCU; `bands` (array of 0–1) weighed between buffered FFT (needs a full block plus real/imaginary scratch before producing anything, periodic CPU spike) and the Goertzel algorithm (one target frequency per band, 2 floats of state each, genuinely one-sample-at-a-time) — Goertzel favored for a visualizer's handful of bands (8–32), losing only against a from-scratch many-hundred-bin spectrograph. Decided not to prove the `Analyzer` in the JS dual-context (worklet + host) simulation at all; building a host-side shadow copy of the render stack purely for analysis surfaced a real bug worth fixing on its own but wasn't worth pursuing further for the `Analyzer`'s sake — it'll be built and proven directly on the MCU.

Real, independent bug found while investigating that shadow-copy idea: `Filter.process()` computed its coefficient from `cutoff / sampleRate`, baking in "this is called exactly `1/sampleRate` seconds after the last call" via the Web Audio global `sampleRate`, inside the class itself. Same mistake found twice more via targeted search: the synth carrier's own phase accumulator (`this.phase += frequency / sampleRate`) and `SoundEvent`'s raw-sample position advance (`samplePosition += rate`, with a comment admitting - but not implementing - that it should scale by real elapsed time). Four wrong turns preceded the real fix, each corrected directly rather than silently: (1) an explicit `dt` parameter threaded through every render signature (`Filter.process(input, cutoff, dt)` etc.) - rejected, a needless second time-step concept alongside existing `clock.delta`; (2) reading `clock.delta` directly instead - wrong because the worklet's `clock.update()` runs once per `process()` callback (once per ~128-sample block), not once per sample, so `clock.delta` is block-granularity, not sample-granularity; (3) `performance.now()` checked and found unavailable inside `AudioWorkletGlobalScope` at all (a deliberately minimal scope, unlike a real `Worker`) - but the equivalent host-side bug was real and fixed on its own merit: `core/system.js`'s `Clock.update()` used `Date.now()` (integer milliseconds, no fractional part) where `performance.now()` (available host-side) gives a true sub-millisecond float, so it was switched; (4) a `SYSTIME()` per-platform high-resolution-time abstraction (with the worklet faking per-sample resolution within one frozen block via a 0-127 counter), driven through `system.loop()` - corrected as conflating two genuinely different loops (`system.loop()`: buttons/game-state/`pixels`, driven by rAF or the MCU main loop; the audio render path: driven by the worklet callback or an I²S buffer-fill request), not a style issue; (5) a dedicated `AudioClock` class, including renaming the worklet's existing local `System`/`Clock` to make the split explicit - rejected under a standing no-rename/no-remove rule.

Final, kept design: `audio.render()` takes no parameters, fills `audio.buffer` (a plain array, already a member, never passed in or returned) in place, advancing a plain `audio.timestamp` field by one sample's duration after every sample - a flat self-advancing counter, not a clock class, correct exactly as long as the buffer-fill callback is never missed or delayed, which the platform already guarantees by contract. No `AudioClock` class, no `dt`, no `offset` anywhere. Every render function (`Sound.render`, `Filter.process`, `LFO.render`, the worklet's `Tracker.render`, `SoundEvent.render`) stripped of all time-related parameters, each reading `this.audio.timestamp` (or `this.tracker.audio.timestamp`) directly in place of `this.audio.system.clock.time + offset`; `process()` itself reduced to a bare loop calling `this.render()` once per sample. With every render call guaranteed once again to be exactly `1/sampleRate` apart (structurally true now, not merely assumed), `Filter`'s and the carrier phase's original `/sampleRate` formulas turned out already correct and were left unchanged - the bug was never in that math, only in what the rest of the engine let call it, and under what assumption.
