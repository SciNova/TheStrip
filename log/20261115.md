# 15 Nov 2026 – Claude Sonnet 5 – Shooters built from scratch, the CSS colour palette lands in all three languages, the panel/keyboard input architecture gets a real fix, three apps go panel-complete, and the whole repo is reorganized into core/apps/drafts

The session opened with a straightforward question — what did we think of the project overall — and ended up touching nearly everything: a brand-new game built entirely through conversation before any code existed, a colour system overhaul that forced its way across JavaScript, Python and C++, a real architectural bug in how keyboard input reached games, and a full repository reshuffle that leaves the codebase in a noticeably more honest shape than it started in.

### Shooters, built target by target

The idea started from nothing more than "a shooting-gallery stand" and was built up entirely in conversation before a line of code existed: a white aim pixel (`Player.location`, a float, rounded only at render time), and `Target` objects that fade in and out via a `visibility` float driving both size and brightness together. Early design decisions were corrected more than once and the corrections stuck: `hit()` started as a bare state-flip but was later reconceived as `check(shot)` — each object testing whether it was actually hit and reacting (and scoring) itself, rather than the game deciding for it; the hit-quality idea (a 0–1 score derived from the target's own state at the moment of impact, e.g. a cat's current speed) was floated and partly built via `hitCount`-style escalation, generalized from "tied to the hit" to "could be tied to anything a class wants to track." A firework-style spark burst (`Spark`, `blendMax` additive blending) was lifted directly from `DemoScene.js`'s existing fireworks rather than invented fresh.

Nine species were designed, each as a thin `Target` subclass differing only in size, colour, and behaviour: `Fly`, `Rat`, `Frog`, `Duck`, `Crow`, `Cat`, `Pot`, `Monkey`, `Balloon`. Movement came in three families — rest/jump (`Frog`, eased landing, re-randomized `patience` and jump distance each cycle), rest/move-at-constant-speed (`Cat`, `Rat`, `Monkey`, each just a retuned copy of the same shape), and continuous wander (`Fly`, `Balloon`, a random-walk on velocity with no rest state at all). `Crow` got the most interesting render: body fixed at normal size and centered on `location` the whole time, with a tail of the same colour extending backward from the trailing edge — sweep amount derived fresh each frame from `sin(time × rate × |speed|)`, not an accumulated phase, so the flap frequency speeds up and slows down exactly with current flight speed. A genuine naming confusion ran through several turns: `hopState` was renamed to `actionState` specifically because `Target.state` already existed for the `ACTIVE`/`HIT`/`GONE` lifecycle — a second field called `state` would have silently clobbered it the instant a frog started jumping.

A real sound architecture got worked out from first principles: the system's shared `Sound` enum is "the base sounds any game gets for free," and a game can declare its own `static sounds` object on its own class (not a separately-exported const) so the loader has one consistent access point — `GameClass.sounds` — without needing per-game special-casing anywhere. `SampleAudio`'s constructor-only sound-loading became a proper, idempotent `load()` method the system calls again once a game is actually assigned, picking up that game's own sounds from its own folder without touching anything for the 40-odd games that don't declare any. Three real croak sounds were generated via ElevenLabs, trimmed from `.mp3` to `.wav` with `ffmpeg` (installed fresh this session), and wired to fire at the exact moment a jump lands — "it is not polish, it eliminates all ambiguity despite the render being ridiculously simple" was the verdict once it actually played, and it held up: a green blob with two dots reads unmistakably as a frog the instant it croaks.

A long, still-unfinished discussion worked out the intended game-progress model — a fixed, hand-ordered array-of-levels manifest (not derived from counters), a concurrency cap gating when the next entry in the sequence can appear, no fail state ever (only a missed-shot penalty against a theoretical maximum score, same philosophy as `Darts`), and a hit-resolution order of obstacles-then-targets-then-a-ricochet-sound-set on a total miss. None of that is built yet — it's design, not code.

### The colour palette becomes real

Partway through giving the targets colours, the project's entire `Colors` enum was found to be invented rather than real — `GREEN` was `0x00FF00` (CSS's `lime`, not `green`), `ORANGE`/`PURPLE`/`PINK`/`LIGHT_GRAY`/`DARK_GRAY` were all off from their real CSS meanings, and several entries (`BANANA`, `LEMON`, `WATERMELON`, the whole `DARK_*` family) had no CSS equivalent at all. The fix was the full 141-entry CSS/X11 named colour list, with a small alias block for genuinely useful non-CSS names (`OFF`, the fruit names `Slots.js` already depended on) and four flagged-bogus leftovers kept only until the handful of games still using them get updated. It was explicitly agreed this would change how existing games look and that this was fine — "we should NOT support everything, but nevermind — the point is that every game references an actual official colour, not a random hex value."

JavaScript became the agreed source of truth, and the same list was manually ported into Python's and C++'s `system.*`, byte-for-byte matching, including the bogus/alias tail and a comment pointing back at the JS source. A JS-only detour — extracting `Colors` into its own `color.js` — was tried, then explicitly reversed later in the session once the bigger reorganization made clear it didn't need to exist as a separate file; it's inlined directly into `system.js` now, matching how Python and C++ always had it.

### The panel/input architecture gets a real fix, not a patch

A confusing naming collision was found and fixed: the old single-button panel was called `A` — "for Action," from early sessions — which collided conceptually with the real, meaningful `A` button on the `ABC`/`ABCD` panels (`Stack`'s red/green/blue buttons, `SimonSays`'s four colours). The old panel was renamed `F` (and its siblings `LRA`→`LRF`, `UDA`→`UDF`), and critically its button now actually emits `Command.FIRE_PRESS`, not `Command.A_PRESS` — a cosmetic rename alone would have left the real ambiguity sitting in the code. `ABC`/`ABCD` were left completely untouched; they're not generic colour panels, they're built to match a specific game's own colour language and were never part of the confusion. A new `LRUDFF` panel (both direction pairs, two fire buttons) was added with a freshly-drawn SVG, its element order in the markup deliberately matching `pressCommands`' order rather than visual layout, since that's what the click-wiring actually depends on. The unused `EE` (dual encoder) panel was dropped from the simulator's selectable set, though the real-hardware concept it represents wasn't deleted from the design — its two push-buttons are understood to just reuse `FIRE`/`FIRE2`, same as `LRUDFF`'s.

A real architectural bug came out of testing this: keyboard keys `1`–`4` were wired through the *panel-dependent* button array (`ControlPad.buttons`, built only from whatever `panel.pressCommands` happens to be) — meaning with no panel selected (the simulator's actual default), those keys silently did nothing. The fix wasn't a default-panel hack (one was tried and immediately rejected — "what is this crap, this is not what i asked, remove that shit, no default panels!!") but the correct architectural separation: `A`/`B`/`C`/`D` joined `UP`/`DOWN`/`LEFT`/`RIGHT`/`FIRE`/`FIRE2` as a second always-on command set (`namedButtons`, parallel to the existing `directionButtons`), completely independent of whichever panel is attached. The panel-derived mechanism was left untouched for its real, narrower job: wiring mouse/touch clicks on whichever specific SVG is actually on screen. "Keyboard just injects a raw press/release, same as clicking a panel's button — the game receives the identical thing either way" was the stated principle, and it now actually holds.

### Three apps taken to genuinely complete, panel by panel

`WhiteLight`, `ColorLight`, and `Moodlight` were each walked through every panel variant and brought to a real, verified "complete within logical limits" state — the first time in the project this checklist existed to check against. All three got the same correction: direction-held brightness/speed control changed from a discrete `±1%` nudge per press to continuous hold-to-ramp (mirrored directly from `WhiteLight` into `ColorLight` and `Moodlight` once the pattern was settled), while encoder input stayed a discrete per-detent step, since a detent is already a discrete event. A deliberate rule was set for colour-button panels: rather than forcing `ABCD`'s four colour buttons into an awkward brightness/hue mapping, all four (plus both fire buttons) were collapsed to a single uniform function — toggle — leaving every other panel to reach whatever subset of functions is physically coherent for it (an `F`-only panel toggles and nothing else; a bare direction-pair panel adjusts one axis and can't toggle at all; the full `LRUDFF`/`EE` panels reach every function).

`Moodlight` surfaced a real design bug along the way: `speed` was allowed to range `-2.0`–`2.0`, with negative values silently reversing the plasma's animation direction. "The zero point is bullshit, that is not speed, that is reversing the direction" — fixed by changing the range to a pure `0.0`–`2.0` magnitude, matching the actual intent ("at max it moves fastest, at 0 it completely stops, that's the whole point").

`MemoryMatch` was read in full and confirmed genuinely complete end-to-end (matching, scoring, level progression, a real terminal state) — with one caveat noted rather than silently waived: its cards are plain object literals (`{ color, revealed, matched }`), not a dedicated class, which is exactly the "fake-ass classes instead of real OOP" anti-pattern the project's own first completion checkpoint exists to catch.

### The repository gets reorganized, twice over

The 44-game roster was sorted for the first time into real categories — `Apps`, `Games` (the deliberately-designed, "done" set), `Devel` (tracked by literal git-dirty state, not a feeling), `Drafts` (everything Claude Code generated in bulk from just a name, unevaluated by design — "even if the code is completely wrong, the name itself is already a valid game idea"), and `2D` — reflected identically in both the web nav and `Games.md`. A four-column completion checklist (`Code` / `Play` / `Sound` / `Panels`) was adopted to replace the old table's stale, internals-focused status notes; language sync and documentation were explicitly *not* made separate checklist items, since sync now happens inline with any change and `Games.md` already *is* the documentation.

The physical folder structure followed: `haxe/`, `c/`, and `arduino/` archived; a new `core/` holding only the genuinely shared API (`system.*`/`graphics.*` across all three languages, nothing hardware-specific); a new `apps/` holding the real product, flat by default, promoted to its own subfolder the instant it needs real assets (as `Shooters` already did), with everything unevaluated living in `apps/drafts/`; `Console.js`/`three.js`/`game.js` moved into `js/`, which now holds only browser-harness-specific code. Every one of the roughly sixty affected files' imports/includes was fixed by hand and verified both with `node --check` and against the actually-running Flask server at each step — including a real bug this surfaced in `web.py` itself, where the `/games/<game>` page route collided with real static files once they briefly shared a folder name with the URL prefix; renaming the physical folder to `apps/` removed the collision outright rather than needing a workaround.

`DicesClock` was renamed `StopWatch` to match what it actually is (no real clock yet, just elapsed seconds), and `Dices` was confirmed to belong in `Apps` rather than `Games` — "it's a utility, not a game in itself; Backgammon or Yahtzee would use it." `GAMES.md` (an untracked, outdated duplicate) was deleted outright; `Games.md` renamed `Library.md`; `DevLab.md` renamed `Development.md`.

### Both reference docs rewritten from the real sources

`Library.md`'s per-app/per-game descriptions were rebuilt one at a time, almost entirely through direct correction — the recurring failure mode was describing internals, rendering details, or button names instead of what a thing actually *is* and what it *does* ("not a psychiatry school," "describing what it is not, not what it is," "stop addressing the reader!!"). The settled shape: a short identity sentence, then a plain bullet list of functions with no button names at all (buttons are a panel-mapping concern, documented nowhere near this), with enumerable lists (demo effects, dice symbols, ghost names) pulled out to the end rather than embedded in prose.

`API.md` — unchanged since the project's Haxe days and aspirational even then (a bitmask input enum, a formal `Controller`/callback system, a `RELEASE` button state, a `defer()` method — none of which the real JavaScript ever actually had) — was rewritten from the real, current `core/system.*`/`core/graphics.*` sources as one language-agnostic reference instead of three, with every class and enum given back its full signature block (every field, every method, one enum value per line) ahead of its prose description, matching the original document's own two-part structure once that got clarified.

### Where this leaves things

Nothing from this session has been committed yet — the three `Shooters`-building commits (`a7ebba6`, `cce32f7`, `a8ef4a6`) landed mid-session and were pushed to `main` under the SciNova account as usual, but everything from the panel rename onward (the colour sync, the keyboard fix, both doc rewrites, and the entire `core`/`apps`/`drafts` restructuring) is still sitting in the working tree. A long session by content, not by elapsed time, by the team's own account — "not as long in time, but much in content, we did a lot."
