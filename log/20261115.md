# 15 Nov 2026 – Claude Sonnet 5 – Shooters built from scratch, the CSS colour palette lands in all three languages, the panel/keyboard input architecture gets a real fix, three apps go panel-complete, and the whole repo is reorganized into core/apps/drafts

We opened the session with a straightforward question — what we thought of the project overall — and ended up touching nearly everything: a brand-new game built entirely through conversation before any code existed, a colour system overhaul that forced its way across JavaScript, Python and C++, a real architectural bug in how keyboard input reached games, and a full repository reshuffle that left the codebase in a noticeably more honest shape than it started in.

### Shooters, built target by target

Nothing but the idea of a shooting-gallery stand kicked this off; we built it up entirely in conversation before a line of code existed: a white aim pixel (`Player.location`, a float, rounded only at render time), and `Target` objects that fade in and out via a `visibility` float driving both size and brightness together. We corrected early design decisions more than once, and the corrections stuck: `hit()` started as a bare state-flip, then we reconceived it as `check(shot)` — each object testing whether it was actually hit and reacting (and scoring) itself, rather than the game deciding for it. We floated the hit-quality idea too (a 0–1 score derived from the target's own state at the moment of impact, e.g. a cat's current speed) and partly built it via `hitCount`-style escalation, generalizing it from being tied only to the hit itself to being tied to anything a class wants to track. For the spark burst on a hit, we lifted `Spark` (`blendMax` additive blending) directly from `DemoScene.js`'s existing fireworks rather than inventing one fresh.

Nine species came out of that design pass, each a thin `Target` subclass differing only in size, colour, and behaviour: `Fly`, `Rat`, `Frog`, `Duck`, `Crow`, `Cat`, `Pot`, `Monkey`, `Balloon`. Movement came in three families — rest/jump (`Frog`, eased landing, re-randomized `patience` and jump distance each cycle), rest/move-at-constant-speed (`Cat`, `Rat`, `Monkey`, each just a retuned copy of the same shape), and continuous wander (`Fly`, `Balloon`, a random-walk on velocity with no rest state at all). `Crow` got the most interesting render: body fixed at normal size and centered on `location` the whole time, with a tail of the same colour extending backward from the trailing edge — we derived the sweep amount fresh each frame from `sin(time × rate × |speed|)`, not an accumulated phase, so the flap frequency speeds up and slows down exactly with current flight speed. A genuine naming confusion ran through several turns before we caught it: `Target.state` already owned the `ACTIVE`/`HIT`/`GONE` lifecycle, so we renamed `hopState` to `actionState` — a second field called `state` would have silently clobbered it the instant a frog started jumping.

We worked out a real sound architecture from first principles: the system's shared `Sound` enum became the base sounds any game gets for free, and a game could declare its own `static sounds` object on its own class (not a separately-exported const) so the loader has one consistent access point — `GameClass.sounds` — without needing per-game special-casing anywhere. We turned `SampleAudio`'s constructor-only sound-loading into a proper, idempotent `load()` method the system calls again once a game is actually assigned, picking up that game's own sounds from its own folder without touching anything for the 40-odd games that don't declare any. We generated three real croak sounds via ElevenLabs, trimmed them from `.mp3` to `.wav` with `ffmpeg` (installed fresh this session), and wired them to fire at the exact moment a jump lands — once it actually played, eliminating ambiguity mattered more than polish, and it held up: a green blob with two dots reads unmistakably as a frog the instant it croaks.

The intended game-progress model took a long, still-unfinished discussion to work out — a fixed, hand-ordered array-of-levels manifest (not derived from counters), a concurrency cap gating when the next entry in the sequence can appear, no fail state ever (only a missed-shot penalty against a theoretical maximum score, same philosophy as `Darts`), and a hit-resolution order of obstacles-then-targets-then-a-ricochet-sound-set on a total miss. None of that is built yet — it's design, not code.

### The colour palette becomes real

Partway through giving the targets colours, we found the project's entire `Colors` enum was invented rather than real — `GREEN` was `0x00FF00` (CSS's `lime`, not `green`), `ORANGE`/`PURPLE`/`PINK`/`LIGHT_GRAY`/`DARK_GRAY` were all off from their real CSS meanings, and several entries (`BANANA`, `LEMON`, `WATERMELON`, the whole `DARK_*` family) had no CSS equivalent at all. We fixed it with the full 141-entry CSS/X11 named colour list, plus a small alias block for genuinely useful non-CSS names (`OFF`, the fruit names `Slots.js` already depended on) and four flagged-bogus leftovers kept only until the handful of games still using them get updated. We agreed this would change how existing games look, and that this was fine — every game needed to reference an actual official colour, not a random hex value, even at the cost of dropping support for a few invented ones.

JavaScript ended up as the agreed source of truth, and we manually ported the same list into Python's and C++'s `system.*`, byte-for-byte matching, including the bogus/alias tail and a comment pointing back at the JS source. We tried a JS-only detour — extracting `Colors` into its own `color.js` — then explicitly reversed it later in the session once the bigger reorganization made clear it didn't need to exist as a separate file; it's inlined directly into `system.js` now, matching how Python and C++ always had it.

### The panel/input architecture gets a real fix, not a patch

A confusing naming collision turned up: the old single-button panel was called `A` — short for Action, from early sessions — which collided conceptually with the real, meaningful `A` button on the `ABC`/`ABCD` panels (`Stack`'s red/green/blue buttons, `SimonSays`'s four colours). We renamed the old panel `F` (and its siblings `LRA`→`LRF`, `UDA`→`UDF`), and critically made its button actually emit `Command.FIRE_PRESS`, not `Command.A_PRESS` — a cosmetic rename alone would have left the real ambiguity sitting in the code. We left `ABC`/`ABCD` completely untouched; they're not generic colour panels, they're built to match a specific game's own colour language and were never part of the confusion. We added a new `LRUDFF` panel (both direction pairs, two fire buttons) with a freshly-drawn SVG, its element order in the markup deliberately matching `pressCommands`' order rather than visual layout, since that's what the click-wiring actually depends on. We dropped the unused `EE` (dual encoder) panel from the simulator's selectable set, though we kept the real-hardware concept it represents in the design — its two push-buttons are understood to just reuse `FIRE`/`FIRE2`, same as `LRUDFF`'s.

Testing this surfaced a real architectural bug: keyboard keys `1`–`4` were wired through the *panel-dependent* button array (`ControlPad.buttons`, built only from whatever `panel.pressCommands` happens to be) — meaning with no panel selected (the simulator's actual default), those keys silently did nothing. We first tried a default-panel hack and rejected it immediately as not the right fix; the real fix was the correct architectural separation: `A`/`B`/`C`/`D` joined `UP`/`DOWN`/`LEFT`/`RIGHT`/`FIRE`/`FIRE2` as a second always-on command set (`namedButtons`, parallel to the existing `directionButtons`), completely independent of whichever panel is attached. We left the panel-derived mechanism untouched for its real, narrower job: wiring mouse/touch clicks on whichever specific SVG is actually on screen. The stated principle — that keyboard input injects a raw press/release exactly like clicking a panel's button, so the game receives the identical thing either way — now actually holds.

### Three apps taken to genuinely complete, panel by panel

`WhiteLight`, `ColorLight`, and `Moodlight` each went through every panel variant this session, landing in a real, verified complete-within-logical-limits state — the first time in the project this checklist existed to check against. We gave all three the same correction, changing direction-held brightness/speed control from a discrete `±1%` nudge per press to continuous hold-to-ramp (mirrored directly from `WhiteLight` into `ColorLight` and `Moodlight` once the pattern was settled), while keeping encoder input a discrete per-detent step, since a detent is already a discrete event. We set a deliberate rule for colour-button panels: rather than forcing `ABCD`'s four colour buttons into an awkward brightness/hue mapping, we collapsed all four (plus both fire buttons) to a single uniform function — toggle — leaving every other panel to reach whatever subset of functions is physically coherent for it (an `F`-only panel toggles and nothing else; a bare direction-pair panel adjusts one axis and can't toggle at all; the full `LRUDFF`/`EE` panels reach every function).

Testing `Moodlight` surfaced a real design bug: `speed` was allowed to range `-2.0`–`2.0`, with negative values silently reversing the plasma's animation direction. The zero point didn't represent speed at all — it was reversing direction — so we fixed it by changing the range to a pure `0.0`–`2.0` magnitude, matching the actual intent: fastest at max, completely stopped at zero.

We also read `MemoryMatch` in full this pass and confirmed it genuinely complete end-to-end (matching, scoring, level progression, a real terminal state) — with one caveat we noted rather than silently waived: its cards are plain object literals (`{ color, revealed, matched }`), not a dedicated class, exactly the kind of stand-in-for-real-OOP shortcut the project's own first completion checkpoint exists to catch.

### The repository gets reorganized, twice over

We sorted the 44-game roster for the first time into real categories — `Apps`, `Games` (the deliberately-designed, done set), `Devel` (tracked by literal git-dirty state, not a feeling), `Drafts` (everything Claude Code generated in bulk from just a name, unevaluated by design — even a wrong implementation still leaves a valid game idea behind in the name alone), and `2D` — reflected identically in both the web nav and `Games.md`. We adopted a four-column completion checklist (`Code` / `Play` / `Sound` / `Panels`) to replace the old table's stale, internals-focused status notes; we deliberately left language sync and documentation off the checklist as separate items, since sync now happens inline with any change and `Games.md` already is the documentation.

The physical folder structure came next: we archived `haxe/`, `c/`, and `arduino/`; created a new `core/` holding only the genuinely shared API (`system.*`/`graphics.*` across all three languages, nothing hardware-specific); created a new `apps/` holding the real product, flat by default, promoted to its own subfolder the instant it needs real assets (as `Shooters` already did), with everything unevaluated living in `apps/drafts/`; and moved `Console.js`/`three.js`/`game.js` into `js/`, which now holds only browser-harness-specific code. We fixed every one of the roughly sixty affected files' imports/includes by hand and verified them both with `node --check` and against the actually-running Flask server at each step — that process surfaced a real bug in `web.py` itself, where the `/games/<game>` page route collided with real static files once they briefly shared a folder name with the URL prefix; renaming the physical folder to `apps/` removed the collision outright, no workaround needed.

We renamed `DicesClock` to `StopWatch` to match what it actually is (no real clock yet, just elapsed seconds), and confirmed `Dices` belongs in `Apps` rather than `Games` — it's a utility, not a game in itself, the kind of thing Backgammon or Yahtzee would use. We deleted `GAMES.md` outright (an untracked, outdated duplicate), renamed `Games.md` to `Library.md`, and renamed `DevLab.md` to `Development.md`.

### Both reference docs rewritten from the real sources

One at a time, we rebuilt `Library.md`'s per-app/per-game descriptions, almost entirely through direct correction — the recurring failure mode was describing internals, rendering details, or button names instead of what a thing actually is and does. We settled on a short identity sentence, then a plain bullet list of functions with no button names at all (buttons are a panel-mapping concern, documented nowhere near this), with enumerable lists (demo effects, dice symbols, ghost names) pulled out to the end rather than embedded in prose.

`API.md` had sat unchanged since the project's Haxe days, and was aspirational even then — a bitmask input enum, a formal `Controller`/callback system, a `RELEASE` button state, a `defer()` method, none of which the real JavaScript ever actually had. We rewrote it from the real, current `core/system.*`/`core/graphics.*` sources as one language-agnostic reference instead of three, giving every class and enum back its full signature block (every field, every method, one enum value per line) ahead of its prose description, matching the original document's own two-part structure once we'd clarified it.

### Where this leaves things

We hadn't committed anything from this session yet — the three `Shooters`-building commits (`a7ebba6`, `cce32f7`, `a8ef4a6`) landed mid-session and we pushed them to `main` under the SciNova account as usual, but everything from the panel rename onward (the colour sync, the keyboard fix, both doc rewrites, and the entire `core`/`apps`/`drafts` restructuring) was still sitting in the working tree. It was a long session by content, not by elapsed time — we didn't spend that much time on it, but packed a lot in.
