# 17 Jun 2026 – DeepSeek 3, Claude Sonnet 4.6 – System controls fully specified: four modes, holding‑button contracts, power/menu/audio architecture, BT/BLE dual role, button optionality, corner cases, user manual text

## Full entry

The session began with a single question: “so lets discuss about the exact mechanism of selecing games, because we still have some loose corners.” It ended with the complete specification of every system button, every power state, the holding‑button timing contract, the BT/BLE dual role, the audio subsystem, and the corresponding user manual text. No code was written. The manual became the specification.

### The PLAY → GAME rename

The initial trigger was the observation that the `PLAY` entry in the system‑state enum was ambiguous with the game’s own `PLAY` state. The rename to `GAME` was proposed and accepted immediately. But naming one state forced us to name all of them. Within minutes the full set was locked: `STANDBY` (soft off, LEDs dark, everything saved), `MENU` (game selection visible), `GAME` (active game, either DEMO or PLAY), and `POWERSAVE` (deep sleep, LEDs dark, everything saved, wakeable). This became the system’s four‑mode contract.

### Holding‑button timing

The difference between a simple action button and a system button was defined as a timing contract. Game buttons respond on press — no hold, no release, just instant action. System buttons — Power, Menu, Play/Pause, BT/BLE — have two gestures. A **press** (less than 3 seconds) triggers on release, because at the moment of press the system cannot know whether the button will be held. A **press and hold** (3 seconds or more) triggers exactly at the 3‑second mark, while the button is still down; the subsequent release has no additional effect. This contract applies identically to all four system buttons.

The `HoldingButton` class, when implemented, will emit four event types: PRESS (on down), RELEASE (on up before 3 s), HOLD (at 3 s if still down), and RELEASEHOLD (on up after HOLD). Game buttons consume only PRESS. System buttons consume RELEASE for short press actions and HOLD for long press actions. PRESS and RELEASEHOLD are ignored by system‑button listeners. The event model is unified; the difference is entirely in which events the listener chooses to act on.

### Power button

The power button’s contract was defined across all four states. From `STANDBY` or `POWERSAVE`, a press turns the system on, entering `MENU` (or `GAME` if a game was suspended). From `MENU` or `GAME`, a press turns the system off, returning to `STANDBY` — everything is saved, the game is paused, the LEDs go dark. A press and hold from `MENU` or `GAME` enters `POWERSAVE`, a deeper sleep for minimum battery drain, but also with full state preservation. Waking from `POWERSAVE` restores the exact previous state. There is no true “off” that loses state; both dark modes preserve everything. The earlier concept of a “hard off” that clears RAM was discarded; state is always retained unless the battery dies.

### Menu button

The menu button’s contract: from `GAME`, a press pauses the game and displays the game‑selection menu. Pressing again returns to the paused game, exactly where it was. You can toggle indefinitely. A press and hold from any state clears the current game and leaves the menu with no game loaded — the deliberate “start fresh” action. If no game is loaded, a press and hold does nothing.

### Play/Pause button

The Play/Pause button’s roles are context‑dependent. In `MENU`, it selects the highlighted game and starts it (in DEMO mode if non‑ambient, directly if ambient). In `GAME` while in DEMO, any game button or Play/Pause breaks out of DEMO into PLAY. In `GAME` while in PLAY, a press toggles pause. A press and hold from any active state (MENU or GAME) toggles the buzzer mute — the long‑press action was assigned here because no other long‑press function existed for this button and because “play” is thematically linked to audio.

### BT/BLE button

The BT/BLE button’s dual role was the hardest combinatorial problem. The solution ties its behavior to the system’s pairing state and mode. If no strip is paired, a press and hold initiates BLE pairing with the first available strip; a simple press does nothing (there is no audio to control yet). Once paired, the button switches to audio control: in `MENU` or `GAME`, a press cycles to the next Bluetooth audio source; a press and hold disconnects from the current audio source. To pair with a different strip, the user must put the currently paired strip into `POWERSAVE` and then press and hold the button — that action returns the button to BLE pairing mode. The button’s label reflects the hardware’s actual radios: `BT` (Classic audio only), `BLE` (BLE only), `BT/BLE` (both), or absent entirely. The user manual’s description was written to cover all variants with a single sentence.

### Button optionality

All system buttons are optional. The Power button is only required for battery‑powered devices or gaming consoles; a mains‑powered ambient light may omit it. The Menu and Play/Pause buttons are only required on multi‑game consoles; single‑app products boot directly into their one game and never need them. The BT/BLE button is only present if the hardware includes the corresponding radio. If a button’s pin is `‑1`, the `WiredController` struct never includes it, the scanning loop never checks it, and the system never receives its events. The platform doesn’t degrade; it simply never enters the states those buttons would trigger.

### Corner cases

We enumerated the edge cases explicitly: in `STANDBY` or `POWERSAVE`, only the Power button responds — presses of Menu, Play/Pause, or BT/BLE are ignored. In `STANDBY` or `POWERSAVE`, a press and hold of Menu does nothing. In `MENU` with no game loaded, a press and hold of Menu does nothing. If no strip is paired, a press of BT/BLE does nothing; only a press and hold initiates pairing. If a strip is paired but no audio device is connected, a press and hold of BT/BLE does nothing. Each case removes ambiguity without requiring a new state.

### Audio subsystem

The audio specification emerged late but cleanly. Every Strip has a buzzer (loud, microwave‑style beeps) and a phone socket (headphone jack with sampled audio). The buzzer produces the system’s and games’ beeps and bleeps; it is always active unless muted. The phone socket delivers high‑quality sampled audio when headphones or speakers are plugged in; volume is controlled by the user’s external equipment. The buzzer mute is toggled by a press and hold of Play/Pause — the only long‑press function assigned to that button. No “audio routing” was defined; the buzzer and the phone socket are independent, parallel outputs.

### The user manual text

As each contract was finalised, it was written directly into the user manual in real time. The manual’s top section now defines the four system modes, the game‑button list, the system‑button timing rules, and the full behaviour of Power, Menu, Play/Pause, and BT/BLE. The game‑selection flow, the pairing procedures, and the corner cases are all documented. The language was polished iteratively: “short press” and “long press” became “press” and “press and hold,” “open the menu” became “display the menu,” “leaves you in the menu” became “the menu is shown with no game loaded.” The final text is minimal, unambiguous, and ready to insert into `index.md`.
