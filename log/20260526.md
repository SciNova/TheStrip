# 26 May 2026 – DeepSeek 3, Gemini 3, Claude Sonnet 4.6 – The chainsaw massacre

It started as a simple test. “Let’s make a completely new game from scratch, just to prove the platform is rock solid.” The idea was to stress every API surface, find the gaps, and fix them. Within hours the first gap appeared — a missing `renderScaled` — and then the ground opened up. The core wasn’t solid. It was carrying years of accumulated garbage: nullable fields leaking across the 1D/2D boundary, a useless `System` container, four separate button handlers, extern classes that blocked testing, and a monolithic file that had become unbrowsable. The decision was instant: bring the chainsaw. What followed was a multi‑day, multi‑assistant architectural massacre that rebuilt the platform from its foundations. By the end, every class had been interrogated, every dead abstraction killed, and every name forced to answer the question “does this thing exist?”. The platform emerged as a genuine, multi‑target game console engine — all under 100k lines of code.

This was not a cleanup. It was a restoration. The work was guided by a philosophy that goes back to the demoscene: Future Crew proved that four kilobytes could hold a universe, and the standard they set has never been surpassed. The same discipline lives in uClibc, which does everything glibc does in a fraction of the size, and in Minix, a complete operating system small enough to teach from a textbook. Jef Raskin dreamed of a computer that was a humble appliance, not a bureaucracy of features. The platform had to meet that standard. There is an ongoing bet that no application should ever exceed 100,000 kilobytes of source code — not as a limit, but as a discipline. The entire platform, including all ten games, sits well under that ceiling. Every line that survived the massacre earned its place. No corporate roadmap would ever approve what was done here; it required a single person with a chainsaw, three LLMs acting as a distributed code review with infinite patience and zero ego, and a refusal to stop until every last piece of dead code was on the floor.

### The 1D / 2D split — nullable fields killed

The first casualty was the false economy of putting `x`, `z`, and `rotation` on a single `Player` class with `null` defaults. A 1D game had no use for depth; a 2D game *required* rotation. Mixing them with nullable fields leaked the 2D system into every simple game. The fix was a clean split:

- **`World`** (1D) holds `size` and `wraps`. **`World2D`** adds `depth`, `wrapsX`, and `wrapsZ`.
- **`BasePlayer`** is the minimal root. **`BasePlayer1D`** adds `location` and a 1D `distance()` method. **`BasePlayer2D`** adds `x`, `z`, `rotation`, a 2D `distance(z,x)`, and a `direction(z,x)` method that returns the absolute world angle.
- **`Shape`** is the pure rendering base. **`Shape2D`** adds `x`, `z`, and a 2D `collides(z,x)` method with toroidal wrapping. **`Square`** and **`Square2D`** follow the same pattern. The `SquareView` static helper avoids code duplication — the single acknowledged exception to the “does this thing exist?” test, forced by Haxe’s lack of multiple inheritance.

The base `Game` class no longer forces a `camera`, `world`, or `player` on any game. Moodlight needs none of them. SimonSays needs only a world. Cars needs a 2D world, a 2D player, and a camera. Every game pays for exactly what it uses.

### Input unification — `handleInput`

Four button methods (`buttonPress`, `buttonHold`, `buttonRelease`, `buttonReleaseHold`) were killed and replaced by a single reactive entry point:

``haxe
public function handleInput(controllerId:Int, input:Input, ?type:InputEvent = null, ?value:Float = 0):Void
``

The `Input` abstract (a bitmask over `Int`) became the definitive catalogue of every possible signal a controller can emit — buttons, D‑pads, encoders, joysticks, and the reserved `Pause`/`Menu` signals. The `InputEvent` enum carries the action type (`ButtonPress`, `ButtonRelease`, `ButtonHold`, `ButtonHoldRelease`, `EncoderLeft`, `EncoderRight`). Joysticks use only the `value` parameter; buttons ignore it. No polling, no state, no naming collisions. Ready for any controller.

### The `Button` state machine and `Controller`

`Button` is a pure logic class that uses `system.clock.time` for debounce (50 ms) and hold detection (1 s). It takes callbacks and a `system` reference, never a `game`. The `Controller` class owns the `Button` instances and wires them to `system.handleInput`. Pause and Menu buttons are permanent, created in the constructor; panel buttons are created per the `PanelModel` enum (`A`, `LR`, `UD`, `ABC`, `ABCD`, `EE`). The platform feeds raw boolean signals into `button.update(true/false)` and the state machine does the rest.

### `Audio`, `Clock`, `Strip` — no longer `extern`

The three hardware service classes were given real, empty bodies and `extern` was removed. `Clock` uses `haxe.Timer.stamp()` everywhere. `Audio` is a silent stub; `SampleAudio` (JS target) extends it with WAV playback. `Strip` is a no‑op. This single change made the platform self‑contained for every target: the browser loads `game.js` and overwrites the empty implementations; Node.js tests run with the defaults; a native C++ binary works identically.

### The `System` OS shell

`System` became the platform’s operating system. It owns `audio`, `clock`, `strip`, `controller`, the active `game`, and an optional `menu` game. Its `loop()` dispatches to whichever is active based on `SystemState` (`MENU` / `PLAY`). `handleInput` routes to the menu or the game. `togglePause()` and `toggleMenu()` are called directly by the permanent pause/menu buttons. The constructor creates the appropriate audio backend via `#if js`. The platform’s canonical `RESOLUTION` constant lives here, with the constructor accepting an optional `resolution` parameter defaulting to `120`. The `Strip` and `Strip3D` classes in `game.js` now take a `system` reference instead of `game`, so the strip can be created before any game is loaded.

### `Game` class stripped

`Game` lost `uptime`, `delta`, `clock`, `camera`, `world`, `player`. It gained a `system` reference and read‑only properties for `audio`, `strip`, and `resolution` that delegate to the system. `isPaused` was replaced by a proper `GameState` enum (`PLAY` / `PAUSED`), and the field was renamed to `gameState` to avoid collision with SimonSays’ own `state` field. The constructor takes only `name` and `system`. `togglePause()` joins the lifecycle methods. The `loop()` uses `system.delta` and `system.uptime` exclusively. No game ever touches raw time again.

### The file split

The 20k‑line monolith was split into five browsable files:

- **`_Audio.hx`** – `Sound`, `Audio`, `SampleAudio`
- **`_Input.hx`** – `ButtonState`, `Button`, `Input`, `InputEvent`, `PanelModel`, `Controller`
- **`_Game.hx`** – `Colors`, `Camera`, `BasePlayer`/`BasePlayer1D`/`BasePlayer2D`, `BaseWorld`/`World`/`World2D`, `GameState`, `Game`
- **`_Graphics.hx`** – `Alignment`, `EdgeMode`, `Shape`, `Shape2D`, `SquareView`, `Square`, `Square2D`
- **`_System.hx`** – `Clock`, `Strip`, `SystemState`, `System`

All files live in the same `haxe/` folder with underscore prefixes to keep them at the top of the listing. Imports are explicit (`import _System.System;` etc.), no wildcards. The platform core is now physically as clean as it is logically.

### The test harness — Node.js and C++ SDL

A Node.js command‑line test (`TestNode.hx`) exercises the entire platform without a browser. It instantiates a `System`, loads a game, and runs the loop, printing `uptime` and `game.time`. A separate C++ target (`TestCpp.hx`) compiles with SDL2 bindings to a native ARM64 ELF that opens a real window showing the 2D world from above — running under Termux inside a Debian proot on a non‑rooted phone, displayed via Termux:X11. The test harness verified every `Player` math function in seconds, ending the two‑day black‑box debugging loops that had plagued earlier sessions.

### The `GameLibrary` and menu model

The menu is just another `Game` subclass. It imports all game files, holds a list of `GameID` values, navigates with `ButtonA`/`ButtonC`, and selects with `ButtonB`. On selection, it creates the chosen game and sets `system.game = newGame`, replacing itself. No special privileges, no system‑level menu code, no circular imports. The platform boots with `system.menu = new GameLibrary(...)` and `system.game = system.menu`. The `System` class handles the `MENU`/`PLAY` state dispatch and the menu‑button toggle, but knows nothing about the menu’s internal logic.

### The browser boot layer — `setup()` / `loop()`

The old `GameController` class was replaced by a pure Arduino‑sketch contract: `System system; setup(); loop()`. The `System.js` file provides `SampleAudio`, `Strip`, `Strip3D`, and the global `setup()`/`loop()` functions. `setup()` creates the `System`, overrides `system.setup` to wire keyboard and create the strip, then loads the game specified by the HTML template. `loop()` calls `system.loop()` and `strip.update()` on every animation frame. The HTML template simply calls `setup()` and `loop()` after loading the platform and the game script. No classes, no ceremony.

### All games ported

Every existing game was updated to the new API: FlappyBird, Moodlight, Stack, SimonSays, Slots, Dices, DicesClock, Dino, Race, Pacman, Maze, and Cars. The pattern was mechanical: remove the `resolution` constructor argument, replace `buttonPress`/etc. with `handleInput`, and update imports. The games themselves were not altered — only their platform bindings changed. All games compile and run correctly.

The `Synth.hx` file remains dormant, awaiting the Audio/Synth hierarchy. The `GameLibrary` menu has not yet been visually implemented on the strip. The C++ SDL test harness needs cleanup and packaging. These are deferred, not forgotten.

The platform is now museum‑grade. Every class exists because it passed the “does this thing exist?” test. The codebase is under 100k lines, supports three targets, and runs ten games. The chainsaw can rest.
