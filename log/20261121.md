# 21 Nov 2026 – Claude Sonnet 5 – The tracker becomes real: MOD playback, a worklet-rendered Tracker class, and the resample bug that took the whole session to find

We turned the Tracker from a browser-only proof-of-concept into a real part of the engine this session: it now renders inside the worklet alongside every other sound, plays actual `.mod` files including their own samples, and exposes exactly where it is in a track to both the host and the worklet at once.

### Starting point: a Test app for the existing oscillator-based Tracker

We built `apps/Test/Test.js` to exercise the Tracker that already existed from an earlier session — FIRE played a booing sample, FIRE2 played/stopped a waltz loaded from ABC. That Tracker scheduled real `OscillatorNode`/`AudioBufferSourceNode` objects directly via the browser's own Web Audio API, which was fine for proving the ABC parser worked but was never meant to be the real engine.

### Settling the Tracker's play API

`play(segment, segments, loop)` took a few passes to land right: a `segment`/`segments` naming collision with the track's own `segments` field, a `startTime` parameter that had no business existing (live sounds always use the current time, never a caller-supplied one), and a real bug where calling `play()` again while already playing scheduled a second, overlapping copy of the track instead of cutting over — fixed by having `play()` act like a seek, canceling whatever was already scheduled first. We confirmed the same primitive covers both a Sonic-style looping level theme and a Simon-Says-style sequence played once through.

### MOD support

We established that a MOD file is the same shape as an ABC tune — a `Track` of `SoundEvent`s — just with real sample-backed instruments instead of synth waveforms. That meant moving `sound` off a per-channel `Track.sounds` array and directly onto each `SoundEvent` (renamed from `NoteEvent` this session), since MOD lets any note pick its own instrument regardless of channel. We built `core/mod.js` from scratch, porting the binary-format logic from the existing `modplayer/` reference: samples, patterns, the order table, `SET_VOLUME`, `SET_SAMPLE_OFFSET`, and reading each file's own initial tempo/speed instead of assuming ProTracker's defaults. Inspecting `faggots_universe.mod` confirmed a classic trick — its sample names are fragments of a scrolling message, not real instrument names.

### The real correction: no Web Audio nodes at all

Partway through getting MOD playback sounding right, we rebuilt the Tracker's actual architecture. A tracker doesn't schedule anything or own any audio object — it renders a value into a channel on every sample, exactly like any other sound, and the audio layer mixes whatever's sitting in the shared channel pool without caring where it came from. `Tracker` moved into `core/audio-processor.js`, the worklet; `SoundEvent` gained its own stateless `render(offset)` there; `Audio` gained a shared `channels` array that both live `Sound`s and `Tracker`s write into directly, summed once in `Audio.render()`. The host side (`core/audio.js`) kept only a thin `Tracker` handle that ships a `Track` and its sample data over once via `postMessage`, then just posts `play`/`stop`.

### Finding what was actually wrong with the sound

Getting MOD playback to sound right took most of the session and several wrong turns before the real bugs surfaced. Two were real, confirmed, and fixed: `mod.js` was hardcoding speed 6 when files set their own (sometimes 2 or 3, roughly doubling the real tempo), and the worklet's `process()` callback was allocating a fresh buffer on every single render quantum, a real GC-pressure source we fixed by pre-allocating once. A worklet-side rewrite of `Sound`'s phase/position math to survive a skipped render call was built, tested, and reverted — real, but not what was actually making MOD playback sound wrong. The actual cause: `SoundEvent`'s sample-position advance works the same simple way `Sound`'s already does, one array element per rendered output sample — correct only if the sample's own recorded data already matches that rate. MOD's raw samples are recorded at 8363 Hz, not whatever rate the engine renders at, so they played back roughly 5.7x too fast — a warm bass or pad sample sped up into something that sounded like a cheap organ. The fix stayed entirely inside `mod.js`: resample each instrument's raw data once at load time, the same way decoding a `.wav` file resamples it before anything ever plays it — nothing in the render path itself needed to know about any rate at all.

### Lifecycle cleanup

Switching games never told the outgoing one to stop anything it had running — a Tracker left playing in the worklet had no way to ever get silenced. We gave `Game` a `cleanup()` hook, called from `loadGame()` right before the old game gets replaced, and implemented it in `Test.js` to stop both trackers.

### Position, in sync, on both sides

We exposed `position` (seconds since `play()`), `segment`, `bar`, and `beat` as real fields on the worklet's `Tracker`, and added matching getters on the host-side `Tracker` that run the identical bar-lookup math independently, against `audio.context.currentTime` rather than any message from the worklet. The two never need to exchange anything live — they're reading the same underlying hardware audio clock already, so they agree on their own, carrying only the fixed, imperceptible lag of the `play` message's own trip across the thread boundary.

### Proving it: mutual exclusion, a progress bar, and a beat indicator

`track.duration` (total track length, computed once at load) let `Test.js` show a growing progress bar across the strip as a track played, which we used to confirm `position` tracked correctly end to end. We replaced it with a beat indicator — one of four 30px strip segments lit for the current beat — which initially looked like it was flashing on bars, not beats. That led to confirming a real fact about the MOD format rather than this file in particular: a beat is 4 rows, not 16, which falls straight out of the standard `BPM = 6 × tempo / speed` formula (the reason MOD's long-documented default `tempo = 125, speed = 6` means literally 125 BPM). We also made the two trackers mutually exclusive — starting one now stops the other first — so only one ever plays at a time.

By the end, both `faggots_universe.mod` and `thumbknack.mod` played correctly, at the right pitch and tempo, switching cleanly between each other, with the LEDs visibly flashing in time with the beat.
