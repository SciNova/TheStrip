# 6 Jun 2026 – DeepSeek 3 Expert – The C platform, input refactoring, and five apps on an ATtiny

What started as a simple question — "why are we still using C++?" — ended with a complete rewrite of the platform into a single‑header C library, a radically slimmed input system, a hand‑tuned assembly driver, and five fully playable applications running on an ATtiny85 with the exact same code that drives a 120‑LED strip on an Uno. The session was a marathon of honest engineering: we killed every C++ abstraction that didn't earn its keep, built a manual OOP discipline in plain C, discovered the exact memory boundaries of the smallest hardware, and proved that a clean, class‑based game console platform can run on a chip that costs less than a cup of coffee. The chainsaw got its final workout, and the platform emerged leaner, more transparent, and genuinely portable.

### The C platform – strip.h

The entire platform core was collapsed into a single header, `strip.h`, written in pure C. The C++ class hierarchy was replaced by a disciplined manual OOP convention: every "class" is a `typedef struct`, every "method" takes an explicit `self` pointer, and inheritance is modelled by embedding a `super` member as the first field. For example, `ButtonEvent` contains an `InputEvent super`, and casting between them is an honest `(ButtonEvent*)` — no hidden vtables, no RTTI, no magic.

The platform's enums were renamed for human readability. Gone are `INPUT_EVENT_BUTTON` and `GAME_STATE_PLAY`; they became `BUTTON_INPUT_EVENT` and `GAME_PLAY_STATE`. Colour constants are now `RED_COLOR`, `BANANA_COLOR`. The `Action` enum got a `NO_ACTION` default so that encoder events can carry a meaningless action without accidentally triggering `A_ACTION`. The naming rule is simple: say what the thing is, left to right, as a person would speak it.

Forward declarations and careful ordering of struct definitions resolved all circular dependencies without touching a single line of logic. The `System` struct holds a `Clock`, an `Audio`, a `Strip`, two `Controller`s, and a `Game*` — all as value members, no dynamic allocation. The `Game` base struct contains resolution, pixels, timing state, and three function pointers (`loop`, `buildStage`, `handleInput`) that serve as manual virtual methods. Every game embeds `Game super` as its first member and wires those pointers in its own init function.

### Input system refactoring

The input pipeline was rebuilt from the ground up. The `Button` class no longer stores a callback or a `self` pointer; it is a pure edge detector. The sketch calls `buttonProcess` with a raw boolean (debounced elsewhere) and receives back a `ButtonEvent` when a press or release edge is detected. The sketch then passes that event to `systemHandleInput` — the single dispatch point for the entire platform.

Debouncing was separated into its own `DebouncedPin` struct, a minimal state machine that filters a single digital signal. The sketch can optionally wrap any physical pin with a `DebouncedPin` and feed the clean signal to the `Button`, or it can use hardware debouncing (RC filter + Schmitt trigger) and skip the software filter entirely. This keeps the `Button` struct completely hardware‑agnostic and trims its memory to just 4 bytes (action + state).

The `Encoder` class was ported from a proven C++ quadrature decoder. It handles the two‑bit Gray‑code sequence of a rotary encoder, debounces internally (using the platform's `DEBOUNCE_DURATION` constant), and fires `EncoderEvent`s with direction (`ENCODER_LEFT`/`ENCODER_RIGHT`). Because the Wokwi KY‑040 simulator produces only simplified falling‑edge pulses rather than a full quadrature cycle, we temporarily disabled the debounce by lowering `DEBOUNCE_DURATION` to zero — the simulator's clean signals didn't need it, and the class sprang to life.

A critical design decision: the encoder carries no action. The sketch, which knows which physical encoder instance fired, stamps the event with the correct action after `encoderUpdate` returns. For the first encoder, it sets `LEFT_ACTION`/`RIGHT_ACTION`; for the second, `LEFT2_ACTION`/`RIGHT2_ACTION`. The game's `handleInput` then simply switches on `ev->action`, exactly as it does for buttons. This keeps the `Encoder` struct pure and the action‑dispatch uniform.

### Memory and the ATtiny85

The ATtiny85 with its 512 bytes of RAM became the platform's proving ground. We mapped the exact memory cost of every component: the `System` struct (with two 16‑button controllers, each carrying two encoders) weighed about 280 bytes; the 30‑LED pixel buffer and its GRB conversion array consumed another 420 bytes (7 bytes per pixel — the irreducible cost of keeping the game in RGB on a GRB strip). We discovered that the platform with Moodlight fits comfortably at 30 LEDs, but 40 LEDs hit the memory ceiling and the strip went blank — a clean, measurable boundary. With simpler apps (WhiteLight) and a 10‑LED strip, we had enough headroom to wire all five buttons and an encoder. The ATtiny wasn't the target; it was the honesty test. And the platform passed.

### Five applications tested

Five complete apps were ported to the C platform and tested on the ATtiny85 (with reduced LED counts) and on an Arduino Uno at 8 MHz with a full 120‑LED strip. Every app compiled from the same `strip.h` and ran without modification.

- **Moodlight** – animated rainbow, ocean, and fire themes. Buttons adjust speed and switch themes.
- **WhiteLight** – a single‑knob dimmable flashlight with smooth fade. All inputs (buttons, encoders, directional) map to brightness or fade toggle.
- **ColorLight** – a two‑knob lamp (brightness + colour temperature/hue). Encoder 1 controls level, encoder 2 adjusts temperature in white mode or hue in colour mode. Dedicated buttons provide quick level changes and mode toggle.
- **SimonSays** – memory game with four colour quadrants, timed playback, and level progression.
- **FlappyBird** – 1D flyer with a single flap action. Any button press flaps the bird; the terrain shifts and the gap narrows over time.

The apps span the platform's full identity: ambient light, interactive appliance, and simple game. Each is a single header file that embeds `Game super` and plugs into the system loop.

### The assembly driver

The hand‑tuned `ws2812b_write.S` was fixed and hardened. A missing `push r28`/`push r29` at the function entry had been silently corrupting the caller's Y pointer — a bug that caused random memory corruption and phantom serial output on the ATtiny. Once fixed, the driver became rock‑solid. It is cycle‑perfect for 8 MHz, hardcoded to the correct port/mask for each MCU (ATtiny85, Uno, Mega) via `#if` blocks, and drives 120 LEDs without a single byte of extra RAM. No Adafruit library, no heap allocation.

### Philosophical underpinnings

Throughout the session, the conversation returned again and again to the project's core philosophy. The platform treats the ATtiny85 not as a limitation but as a certification: if it runs there, it will run anywhere. The code is under 100 KB total. Every byte earns its place. The design follows Jef Raskin's "humble appliance" ideal — no hidden modes, only visible states; no long‑press secrets, no context‑dependent button meanings. The same `strip.h` that drives a 120‑LED gaming experience on an Uno will run on an ESP32 with 4 MB of PSRAM with zero changes.

The platform is now a genuine, multi‑target game console engine written in honest C. It runs on an ATtiny85, an Arduino Uno, and is ready for any chip with more resources. Five applications are complete and tested. The input system is clean, the rendering pipeline is minimal, and the assembly driver is correct to the cycle. The chainsaw has done its work. The platform is ready for a library of games.
