# 18 May 2026 – DeepSeek 3.2 Expert – Pixel type unified: null‑as‑transparent, packed integers, Colors.None killed, RotatingCube base, Dices rebuilt

### The hidden debt

Since the earliest days `Colors.None` was defined as `0x000000` — exactly `Colors.Black`. Every pixel buffer stored `[R,G,B]` triples, and the transparency check in `NewDisplayObject.render()` was `if (src[0] != 0 || src[1] != 0 || src[2] != 0)`. Any object that intentionally used black as a visible colour (dice pips, dark gradients) would have those pixels silently skipped. The casino‑green background bled through the pips, turning them green. The bug had been present since the `DisplayObject` pipeline was introduced but was masked because no game had yet drawn real black on a non‑black background.

### The fix: `null` is transparent, packed integers everywhere

The root cause was the conflation of two concepts into one integer. The fix separates them permanently:

- **`null` means nothing.** No pixel. Transparent.
- **Every integer, including `0x000000`, is a real drawable colour.**

The `Colors` class was re‑typed: every constant is now `Null<Int>` instead of `Int`, with `Colors.None = null`. The standalone `rgb()` function accepts `Null<Int>` and returns `[0,0,0]` for null inputs.

Every pixel buffer in the platform was unified to `Array<Null<Int>>` — a single packed‑integer representation. This touches `App.pixels`, `NewDisplayObject.pixels`, `DisplayObject.pixels`, and every game's render loops. The transparency check in `NewDisplayObject.render()` is now simply `if (src != null)`. `correctLuminance()` takes and returns `Null<Int>`, unpacking and repacking internally.

`App.clear()` now fills the canvas with `Colors.Black` (a real black, not a transparent sentinel). `NewDisplayObject` buffers initialise to `null`.

### `Game.delta` exposed

A secondary debt was cleaned: subclasses like `Dices` needed per‑frame delta time for physics. `Game.loop()` already computed `time - previousTime` internally to update `levelTime`, but the delta was a local variable and vanished. Rather than recompute it in every subclass, `Game` now exposes `public var delta:Float`, set during `loop()`. All subclasses use `delta` directly. No new fields in any game, no “previousTime” copies, no wall‑clock confusion.

### `RotatingCube` base class

The dice projection logic — a square prism with 4 physical sides but an arbitrary number of faces (6 for standard dice, up to 10 for dice‑clock displays) — was extracted from the old `Dices` game into a reusable `RotatingCube` class extending `NewDisplayObject`. Key design:

- Constructor takes `(app:App, faces:Array<Array<Null<Int>>>)`. No sides parameter — always 4 sides.
- Each face pattern is an array of packed nullable ints; length must be odd (CENTER alignment).
- Buffer size is `Math.ceil(faceSize × √2)` forced odd — the maximum projection width at 45°.
- `rotation:Float` (0–1) represents a full **face cycle**, not physical angle. For 6 faces on 4 sides, one face cycle = 1.5 physical revolutions.
- `update()` fills the local buffer with the two‑face projection, clearing unused pixels to `null`. Intensity‑based shading is applied per pixel from the packed colour.
- `quarterRotation = (rotation * faceCount) % 1.0` correctly maps the face cycle to the physical square rotation.

### Dices rebuilt

The `Dices` game was rewritten from scratch around `RotatingCube`. Two `Dice` objects (subclass of `RotatingCube` providing 6 standard pip patterns) are placed at 1/3 and 2/3 strip positions on a casino‑green (`Colors.DarkGreen`) background. A two‑state machine (`IDLE`, `ROLLING`) drives the physics:

- Button press in `IDLE` assigns each die independent random speed and spin duration.
- During `ROLLING`, each die spins at constant speed until its duration expires, then decelerates linearly (`DECELERATION = 6.0 face‑cycles/s²`) to zero, then snaps to the nearest face centre.
- `TICK` fires on every face‑boundary crossing; `CHECKPOINT` fires when each die stops.
- When both dice are stationary, state returns to `IDLE`. No win/lose logic — pure dice rolling.

The black pip dots now render correctly against the green table because the platform treats `Colors.Black` as a real colour and `null` as transparent.

### All games updated to unified pixel type

Every game was updated to use packed integers and `null` transparency:

- **Stack**: `Dot`, `Bullet`, and the main render loop now use packed ints. Explosions and trails write `null` for empty pixels.
- **Slots**: `Wheel.update()` packs fruit colours with parabolic brightness into the local buffer. Payline markers use `correctLuminance(Colors.White)`.
- **Race**: `Player.update()` fills trail gradient as packed ints with `null` for unused pixels. Progress bars and result bars use packed colour constants.
- **SimonSays**: `display()` writes packed colours for the four quadrants and the active tone.
- **Pacman**: Pellets, player, and ghosts use packed colours; `Colors.None` is now `null`.
- **FlappyBird**: Background, terrain, and bird all use packed colours.
- **Moodlight**: Theme render loops pack RGB directly into `app.pixels`.

### JavaScript visualisers updated

Both `Strip` and `Strip3D` in `game.js` were updated to read the new packed‑integer pixel format. The 2D strip unpacks with bit shifts; the 3D strip passes the packed integer directly to `topMaterial.color.setHex()`. The obsolete grey‑floor rescaling and all duplicate 3D strip class definitions were removed.

### Outcome

The platform now has a single, consistent pixel type. Black is black. Transparent is `null`. The `Colors` class is internally consistent (`None = null`, every other constant is a real colour). The dice render correctly. The rendering pipeline is simpler, faster (no per‑pixel array allocation), and semantically correct. The `RotatingCube` base class is ready for dice‑clock and split‑flap display games. `Game.delta` eliminates delta‑recomputation from every subclass. All eight games compile and run.

### Remaining

The old `DisplayObject` class (position‑based, `render()` without parameters) is still present for backward compatibility. Stack, Slots, and older games still use it. The migration path to `NewDisplayObject` is proven (Race, Dices) but not yet applied universally. `RotatingShape` remains the physics primitive for non‑cube rotating objects.
