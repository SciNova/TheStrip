# 27 May 2026 – DeepSeek 3 – Dino rebuilt: resolution‑scaled constants, jittered building placement, object clutter by coverage

The session opened with Dino still carrying raw magic numbers from its original 120‑pixel design, a `Player` class that managed its own delta timer, and a `buildStage()` that used an ad‑hoc gap‑based spawner. By the end, the game had a complete set of resolution‑scaled constants, a clean player aligned with the platform’s `BasePlayer`, a jittered building distribution with guaranteed minimum gaps, an object‑placement model driven by coverage percentage rather than fixed counts, a corrected fisheye shadow, and a proper `COMPLETE` state added to the engine core. Collision detection was left for later, and a persistent object‑overlap artifact was identified but not fully resolved.

### Platform: `Game.delta` and `GameState.COMPLETE`

Two small but necessary additions were made to `_Game.hx`. A public `delta` getter — a single line returning `system.delta` — was added so that game objects like `Player` could read per‑frame time without receiving it as a parameter. The `GameState` enum gained a third variant, `COMPLETE`, and the existing `pause()`, `play()`, and `togglePause()` methods were guarded to do nothing when the game is already in that terminal state. The clock freezes automatically because `Game.loop()` already only advances time when `gameState == PLAY`, so no other changes were needed in the core.

### Player: `BasePlayer` and the death of `dt`

We rewrote `Player` to extend `BasePlayer`, replacing the `isJumping` boolean with a proper `PlayerState` enum (`RUNNING`, `JUMPING`). The `update()` method lost its `dt` argument and now reads `game.delta` directly through the new getter. The pixel buffer — allocated once at `PLAYER_MIN_FRINGE + PLAYER_FRINGE`, forced odd — is filled every frame with a centred bar whose length and brightness encode jump height. The `render()` method blits with `Alignment.CENTER` and `EdgeMode.CLIP`, deliberately without `correctLuminance` to preserve the original colour values. We also renamed the old `speed` field to `jumpSpeed` to avoid confusion with the game’s horizontal scroll speed.

### Constants: every magic number expressed in terms of `game.resolution`

All game parameters that originated from a 120‑pixel canvas were rewritten as fractions of `game.resolution` and assigned in the constructor, since Haxe does not allow `this` or instance members in field initialisers. The speed constants became `1/4 * resolution` (start) and `1/2 * resolution` (end). Building widths became `4/120 * resolution` through `12/120 * resolution`; object widths `4/120 * resolution` through `24/120 * resolution`. The player’s fixed on‑strip position was set to `1/3 * resolution`. Both obstacle and player fringes — the visual extension added by height — were defined as `15/120 * resolution`, with the player’s minimum visible size at `3/120 * resolution`.

We removed the old `LEVEL_CLEARANCE` constant, which computed a speed‑dependent clearance zone. In its place, we introduced two purely geometric clearances: `LEVEL_START_CLEARANCE = 1 * resolution` (one full screen) and `LEVEL_END_CLEARANCE = 1/3 * resolution` (the same fraction as the player’s screen position). Buildings are placed only in the space between these boundaries, guaranteeing the first screen of every level is always empty and the final third of the last screen is clear.

### Building generation: sequential jitter with guaranteed gaps

The `buildStage()` method generates the entire 12,000‑pixel world (10 levels of 12.5 screens each) once, guarded by `time == 0`. Building counts interpolate linearly from 7 to 15 per level, with stochastic rounding — the integer count is the floor of the interpolated float, with a random roll against the fractional part to decide whether to add one.

Buildings are first placed with their centres evenly spaced between `levelStart + LEVEL_START_CLEARANCE` and `levelEnd - LEVEL_END_CLEARANCE`. Then the middle buildings are jittered sequentially: each building is moved randomly between a left bound (`previous building’s centre + minGap`) and a right bound (`next building’s original position - minGap`), where `minGap = MAX_BUILDING_WIDTH + MIN_OBJECT_WIDTH`. Because each new building uses the already‑jittered left neighbour as its reference, the minimum gap is enforced for every pair. The first and last buildings remain fixed at the clearance boundaries.

Each building’s forbidden zone for object placement is stored as `3 * geometricLength`, where `geometricLength = width + (height > 0 ? floor(height * OBSTACLE_FRINGE) : 0)`. This reserves space for the building itself plus a full‑length fisheye shadow on both sides, ensuring that no ground object will ever overlap the building’s dynamic shadow no matter where it scrolls on the strip.

### Object generation: coverage‑based instead of count‑based

We replaced the interpolated object‑count model with a single constant, `OBJECT_COVERAGE = 1/4`. The algorithm computes the raw floor length remaining after subtracting all building forbidden zones, sets a target total width equal to one‑quarter of that floor, then places objects of random width until the target is reached.

Objects are placed by random sampling within the level’s full length (including start and end clearances), with a mandatory edge gap of `MIN_OBJECT_WIDTH` from every already‑placed item. If an object’s initially chosen width cannot fit anywhere, it is repeatedly halved until it reaches `MIN_OBJECT_WIDTH`. If even that minimum width cannot be placed, the algorithm gives up on that object. The colour is chosen randomly between `Colors.Green` and `0x8B4513` (a brown).

This model naturally produces larger objects in early levels where buildings are sparse, and smaller objects in later levels where space is tight, while keeping the overall visual clutter consistent across the game.

### Rendering: fisheye shadow corrected

The fisheye shadow, which had been broken during an earlier unrequested refactoring of the obstacle rendering, was rebuilt. The shadow now extends from the **visible building edges** — computed from `obs.width`, not from the pixel‑buffer edges — toward the strip centre. The shadow colour is `0x333333`, and its length scales with the obstacle’s distance from the centre.

We also added alternating screen backgrounds (`Colors.Black` / `0x333333`) to the rendering loop for debugging purposes, making screen boundaries visible as the world scrolls.

### Game completion: `COMPLETE` state wired

When the camera’s `location` reaches the total distance (`LEVELS * LEVEL_LENGTH * resolution`), the game plays `Sound.GAME_COMPLETE`, sets `gameState = COMPLETE`, and the loop returns immediately on subsequent frames. The screen freezes on the final rendered frame.

### Attempted and rejected

We made multiple attempts to extract the building and object placement logic into separate methods (`placeBuildings()`, `placeObjects()`). All were rejected because they either required parameters or introduced new instance fields to share state. The placement code remains inline in `buildStage()`.

### Unresolved

A persistent artifact remains where ground objects occasionally visually touch or overlap on the strip, despite the distribution algorithm guaranteeing a minimum edge gap of `MIN_OBJECT_WIDTH` in logical coordinates. The cause — likely a mismatch between the logical widths used in placement checks and the final rendered sizes after odd‑sizing — was discussed but not fixed by session end. Collision detection remains commented out.
