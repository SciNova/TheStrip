# 24 Nov 2026 – Claude Sonnet 5 – Strip resolution made configurable end to end, and the menu-thumbnail question resolved into "scale the games, don't hand-draw icons"

This entry is being written incrementally, one section per completed thread, instead of all at once at session end — so a mid-session compaction can't lose anything not yet written up.

### Menu ideas: power sound, circular carousel, and the snapshot/`.px` format

Three menu-related ideas were discussed and judged good, not yet implemented. A JBL-speaker-style distinctive synth chime for power on/off was proposed and agreed worth doing early, as a cheap, high-payoff brand mark, using the existing synth engine — a short (<1s), 2–3 voice, mirrored rising/falling pair.

A 2D-depth circular menu was proposed, modeled on `drafts/Test/Test.js`'s existing "4 rotating bands" prototype: each band is an equal angular slice of a disc, projected onto the 1D strip via `x = center + r·sin(θ)`, with depth (`z = r·cos(θ)`) driving brightness, so a band crossing the strip's center is both brightest and fastest-moving, dimming and slowing near the edges as it goes "around the back." Reusing this projection for menu entries (selected entry at center = brightest + fastest) was judged a good fit, with one caveat flagged: `Test.js`'s rotation is driven by continuous time, but a menu needs discrete, eased transitions between selection indices instead — and that eased tween should stay linear, since the projection's own sine curve already supplies the deceleration near the edges; easing both would double up and feel like it drags.

The `.px` snapshot format (`python/px/*.px`, raw RGB dumps of the live strip, converted to inline SVG for docs via `python/px2svg.py` into `python/px/snapshots.md`) was examined to settle whether snapshots could serve as menu-entry thumbnails. Conclusion: no, not for sparse/pixel-based games (Dino, FlappyBird, Race, Stack, Dices, Slots) — a snapshot is "what the strip looked like at one instant," and shrinking it loses single-pixel accents entirely; it works fine for gradient/field games (Moodlight, SimonSays) where there's nothing discrete to lose. The first conclusion was "hand-craft a menu icon per game" — superseded by the next thread.

### Resolution scaling investigated as the real fix, not hand-drawn icons

Reframed: instead of hand-drawing a menu icon per game, scale the actual game down and use a live snapshot at menu-thumbnail resolution — reusing real gameplay instead of a static asset. Checked across every game in `apps/` (`ColorLight`, `Darts`, `DemoScene`, `Dices`, `Dino`, `FlappyBird`, `Moodlight`, `Pacman`, `Race`, `SimonSays`, `Slots`, `Stack`, `StopWatch`, `WhiteLight`) and confirmed none hardcode pixel indices — all geometry already derives from `this.resolution`, so "just run at a lower resolution" is architecturally plausible without a rewrite. The caveat: each game has its own real minimum legible resolution (WhiteLight/ColorLight/Moodlight scale to 1px; SimonSays to 4 LEDs, since its mechanic is "which of 4 quadrants lit"; Stack/Dino/FlappyBird/Pacman/Race/Dices/Slots each have a minimum pixel budget for their discrete objects below which the mechanic itself breaks, not just looks worse) — to be found empirically per game, not assumed globally. Where a game's floor is still too coarse to read well as a thumbnail even though technically playable, that's the (narrower) case where a hand-drawn icon remains the fallback.

### Resolution made a real constructor parameter, end to end

Decided: a resolution picker belongs in the UI, usable only while the system is `OFF` (mid-game resolution changes are nonsensical — every game's state is sized against the old resolution), and picking one just builds a new `System` from scratch; nothing is preserved across a resolution change.

The change spanned three files. In `core/system.js`, `System`'s constructor now takes `resolution = 120` (previously `new Strip(60)` was hardcoded, overridden ad hoc in `index.html`); the audio-worklet-side `System` (`core/audio-processor.js`) was deliberately left untouched, since it only ever touches `sounds`/`trackers`/channel bookkeeping via `system.game ?? system`, never strip/pixel geometry, so threading resolution through it would be a no-op parameter. In `js/Console.js`, `Console`'s constructor now takes `resolution` and forwards it to `new System(resolution)`; its document-level `keydown`/`keyup` listeners were split out of the constructor into `registerHandlers()`/`deregisterHandlers()`, which turned out to be necessary rather than cosmetic — the original code did `document.addEventListener('keydown', this.handleKeyDown.bind(this))`, throwing away the bound reference immediately, which meant those two listeners could never have been removed by any code, ever. Bound references are now stored (`this._boundHandleKeyDown` etc.) so `deregisterHandlers()` has something real to remove, mirroring the pattern `StripView3D.cleanup()` already used correctly for its own container-level listeners. In `index.html`, `bootstrap()` was renamed to `init(resolution)` (the old name implied a staged startup sequence it never actually had; it only ever builds a console), and it now tears down the previous `Console`'s handlers, if any, before constructing a fresh one, with the old `if (cnsl) return;` early-exit guard dropped so it's callable repeatedly, once per resolution change — guarded instead against being called while the system isn't `OFF` (`SystemState` imported in, replacing an unused `Strip` import once the manual `cnsl.system.strip = new Strip(120)` override line was deleted). `loadGame()`'s own call was changed to only call `init(120)` if no console exists yet, so loading a game from the nav doesn't blow away an already-chosen resolution.

### Four resolution buttons added to the UI, and the CSS debugging that followed

Four buttons (120/60/40/30) added above the existing `panelSwapHome`/`panelSwapGuest` (`+`/`-`) buttons, each calling `init(N)` directly via inline `onclick`. Styled to match the existing `#panelSwapHome`/`#panelSwapGuest` look (36×36 → later 30×30, `#444` background, rounded).

Two real bugs surfaced during layout review from a phone screenshot. First, the new row's rightmost button stopped short of the screen edge while the row below it (`+`/`-`) went flush to the edge — a genuine offset mistake, not a matter of alignment "by eye," read correctly as "a blank button" missing from the end of the top row; fixed by recomputing the row's `right` offsets so both rows share the same right edge. Second, buttons visibly rendered larger than their declared size, with what looked like extra padding around the text — native OS/browser button chrome applying its own default sizing/inset regardless of an author `padding: 0`. Fixed with the standard (non-vendor-prefixed) `appearance: none` plus `box-sizing: border-box`, after an aborted first attempt that also added `-webkit-appearance: none` and was told flatly not to, since `appearance: none` alone is standard, Baseline-supported CSS. The button size itself was also reduced, which is what was actually being asked for by "smaller padding" once it became clear the visible whitespace was the box itself, not internal padding, since `padding` had already been `0`; row offsets, and the previously-unnoticed `#debug` panel (which happened to collide with `debugToggle` after an earlier, unrelated row-shuffle), were recomputed to match. Font size was also unified across `menuToggle`/`res*`/`panelSwapHome`/`panelSwapGuest` to match the existing `debugToggle` ("LOG") button, and the four new buttons were wired into the existing `resetFade()` opacity-fade cycle alongside the other top-bar buttons, both on request.

Separately, the buttons initially did nothing at all when pressed — `index.html`'s script is `type="module"`, so `init`'s function declaration is module-scoped, not attached to `window`; the inline `onclick="init(60)"` handlers run in global scope and couldn't see it (the existing `loadGame` avoided this by being explicitly assigned `window.loadGame = ...`). Fixed by keeping `init` as a normal declaration (so the module's own internal calls to it still resolve) and adding `window.init = init;` right after it, exposing it the same way `loadGame` already was.

### Going game by game: WhiteLight/ColorLight/Moodlight, Slots, Darts, SimonSays, Stack, FlappyBird, Dino, DemoScene

With all four resolutions live, each game was checked against them and sorted into categories: scales smoothly with no floor worth caring about (WhiteLight, ColorLight, Moodlight — fields/gradients, nothing discrete to lose); scales correctly but hits a human playability floor rather than a geometry bug (Darts, Stack, Dino — all derive their geometry from `resolution` correctly, they just become too small/fast to fairly play before the geometry itself breaks); and Slots, matching the playability-floor category too, with its fixed-pattern fruit symbols pixelating before the wheel mechanic itself suffers. SimonSays was confirmed exact and lossless down to 4 LEDs, since its mechanic is just "which of 4 quadrants lit."

DemoScene was checked stage by stage (only the `ACTIVE_STAGES` subset matters: Fireworks, Aurora Borealis, Copper Bars, Scanner, Reactive Burst, Bouncing Balls) and turned up two real hardcoded-absolute bugs: `Firework.burstRadius` and `BouncingBall`'s radius range were both flat pixel constants rather than derived from `resolution`, so a burst or a ball would blow up to take over most of a low-resolution strip instead of shrinking proportionally. Both fixed, expressed as ratios of `resolution` instead. A third, softer case was flagged but left alone: `BOUNCE_GRAVITY` and Reactive Burst's `drag` are absolute velocity/acceleration constants acting on positions that do scale with `resolution`, so motion speed relative to strip length subtly drifts with resolution — nothing visibly breaks, so left as an open question rather than fixed outright.

### Dices: face size vs. buffer size, and the real resolution floor

Asked directly: what's a die's actual rendered width at 45°, and what's the gap between the two dice? Traced through `Square`'s rendering math (`core/graphics.js`) to the real numbers, which led to the actual insight — the 15-pixel hand-authored face pattern is pixel-perfect art that cannot be rescaled, while `Square`'s internal buffer (23px, padded to safely hold the widest possible rotated content) is a separate, larger number that has nothing to do with the face itself. The original layout had been computed against that padded buffer, which was the wrong basis entirely.

The corrected model: budget layout space against the real 15px face, divide whatever's left over by 3 (margin, gap, margin) clamped at zero, and accept that a spinning die's content can reach 20px at 45° — wider than its 15px budget — meaning brief overlap with a neighboor is geometrically unavoidable once the gap gets small. Rather than fight that, the existing last-write-wins behavior of `Shape.render()` (confirmed: it skips `null` source pixels but overwrites non-null ones unconditionally, with no blending) was used deliberately — whichever die is mid-spin now renders first, and the stopped die renders last, so a settled face always wins any overlap instead of being overwritten by a neighbor's sweep. This dropped the real geometric floor to resolution 46 (`2×23`, where margins and gap all reach exactly zero), correcting an earlier, wrong estimate of 60. Confirmed playable, if visually tight with no breathing room, all the way down to 30. A real off-by-one bug surfaced along the way: the center-of-an-odd-length-run formula had used `faceSize/2` instead of the correct `(faceSize-1)/2`, overshooting by half a pixel and rounding into a full extra pixel of shift — visible as a stray uncovered background pixel at resolution 30 once the gap hit zero. Fixed.

### StopWatch becomes a 4-digit display, groundwork for a future clock

Asked for the digit face size used by `StopWatch` (21px, from its own `DIGIT_PATTERNS`), which led to the realization that the Dices lesson generalizes: an earlier (wrong) calculation, based on the padded rotation-buffer diagonal, had concluded 4 digits couldn't fit in 120px at all — but budgeting against the real 21px face instead, the same way Dices now does, fits 4 digits comfortably with room for a colon. `StopWatch` (kept under that name, though it's really the prototype for an eventual RTC clock) was expanded from 3 digits to 4 (tens/ones minutes, tens/ones seconds), with the margin/gap formula generalized to any digit count `n` rather than hardcoded for 3. The real floor for a full 4-digit display lands at 84px — below that, even a zero gap isn't enough, confirmed directly: 3 digits alone already exceed a 60px strip. Colors were changed to match Dices' palette (white segments on a dark background), with the background swapped from green to blue specifically to avoid reading as a casino/poker-table color. A colon-centering bug was then found from a phone screenshot: the colon's position had been computed as the naive midpoint of the two flanking digits' rounded centers, which doesn't reliably land in the actual integer-pixel gap between their rendered edges; fixed by deriving it directly from that real gap instead.

### ABC/ABCD panel menu navigation, and a keyboard Fire shortcut

Noticed: the system menu could be browsed and selected with an LR+Fire-style panel, but not with an `ABC`/`ABCD` panel at all, since those only ever emit `A_PRESS`/`B_PRESS`/`C_PRESS`/`D_PRESS` — never `LEFT`/`RIGHT`/`FIRE`. Fixed in `Menu.handleInput()` and `System.handleCommand()`: `A_PRESS`/`B_PRESS` now move the menu cursor left/right alongside the existing `LEFT_PRESS`/`RIGHT_PRESS`, and `FIRE_PRESS`/`FIRE2_PRESS`/`C_PRESS`/`D_PRESS` all confirm a selection — with no change at all to in-game input, since every one of those still falls through to the active game's own `handleInput` exactly as before once a game is loaded.

Separately, a keyboard `Enter` shortcut was added for Fire, wired as an alias of the existing `'5'` key — which drives the literal `FIRE` direction index directly, independent of whatever panel is configured, as opposed to the panel-dependent named-button path that keys `'1'`–`'4'` use.

### 3D view: how the camera actually works, and where it needs to go

Looked at how `StripView3D` (`js/Console.js`) currently works: the strip itself never moves, and the camera orbits it, with its position computed from spherical coordinates (`cameraRadius`/`cameraTheta`/`cameraPhi`) and its orientation always derived from `camera.lookAt(lookAtPoint)` rather than stored independently — so there's no real "camera orientation" variable today, just a position plus a fixed gaze target, and the strip has no placement (position/orientation) of its own at all.

This came up because of a bigger idea: being able to place the strip in different real-world mounting positions (horizontal near a ceiling, above or below a TV, vertical in a corner or on a wall, flat on the floor facing the player, or flat on the floor sideways) and fly the camera around freely for things like social-media video — not just orbit a fixed point. The conclusion: both the strip and the camera need independent position and orientation, with the current orbit behavior becoming one *mode* of driving the camera (useful for inspection) rather than its only representation; a scripted flythrough is the same two ingredients — a position curve and an orientation curve — sometimes coupled (orbit: position traces a circle, orientation always looks at the center) and sometimes fully independent (a free cinematic path). None of this has been implemented yet — it's groundwork for the room/placement work to come.

### Room plan: dark gray wireframe room, black strip body

Settled on a visual approach for the eventual room mockup: a wireframe-only room (walls, a floor grid, a simple TV outline) in a darker gray than the scene background, keeping color exclusively for the strip and its LEDs so the strip reads as the one real object in an otherwise abstract space. The background itself was changed to a dark gray (from pure black), and the LED strip gained a physical body of its own for the first time — a thin black backing slab sitting behind/under the LED row, since up to now the LEDs floated with nothing behind them.

Sizing that backing slab led to pinning down the 3D view's actual scale for the first time. The LEDs (previously round cylinders, now simple squares with square, not rounded, corners) and their backing are now expressed in literal millimeters rather than arbitrary scene units — 4mm LED footprint, 5mm pitch between LEDs (matching the real spacing described), 0.5mm LED thickness, and a backing slab half that thick (0.25mm) and a full 5mm wide (matching the pitch, not just the narrower LED footprint). Everything else in the 3D view that depends on distance — camera radius and its zoom limits, light positions and falloff distance, the camera's near/far clipping planes — was rescaled by the same factor so the whole scene is now consistently in millimeters, ready for the room itself (walls at realistic meter-scale distances) to be added on the same footing.

### A dedicated button to hide the UI for recording

Added a standalone toggle button, separate from any fullscreen control, for recording clean video of just the strip (and optionally the debug log window): a small eye-icon button fixed in the lower-right corner, clicking it adds a `hiddenUI` class to the page body that hides every other control button and the nav menu outright. The toggle button itself stays in the same spot and stays clickable, but fades down to nearly invisible rather than disappearing, so it can be found and pressed again from memory to bring the controls back.

### Current state

All four resolutions are live and working in the UI. Most games have now been individually checked and categorized by how they handle scaling; DemoScene, Dices, and StopWatch all needed and received real fixes along the way. Pacman, Race, and a true floor-finding pass for Dices below 30 remain unchecked. The 3D view's scale is now real millimeters and its strip has a physical body, but placing the strip in different room positions/orientations, and building the room itself, are still ahead.
