# 20 May 2026 – DeepSeek 3.2 Expert – The great unification

The platform has been taken apart and put back together in a single continuous session. Every game touched, every legacy abstraction killed, and the Haxe side now mirrors the C++ architecture exactly. The whole thing weighs 71 KB. This is the session where it all snapped into place.

### App and Game merged

It started with a simple question: why do we have both `App` and `Game`? The original split was meant to separate ambient apps from level‑based games, but it had been causing friction for months. Moodlight and Slots don't use levels, so they extended `App` directly. But Stack, Race, SimonSays — they all needed `levelTime`, and the display objects that used it had to cast `app` to `Game` or store a separate `game` reference. The split was creating more mess than it solved. The answer turned out to be obvious once stated: every app is just a game stuck at level 0 forever. Moodlight never calls `nextLevel()`; `levelTime` sits at zero harmlessly. So we merged them. `App` and `Game` became a single `Game` class, and every game now extends `Game`. The file stays named `App.hx` — it sits at the top of the directory listing, always visible — but the class inside is `Game`. The old `App` type disappeared entirely, and with it every cast, every `Dynamic` hack, every awkward workaround.

### Rendering classes cleaned

While we were at it, the rendering classes got the same treatment. `NewDisplayObject` was the real one all along — position passed at render time, edge modes, the clean separation of game logic from pixel blitting. The old `DisplayObject` with its stored `position` field was only still around because Slots hadn't been migrated. We moved Slots over, deleted the old class, and renamed `NewDisplayObject` to `DisplayObject`. One rendering primitive, exactly what the platform needed. `RotatingShape` went too — dead code from the January dice experiments, completely superseded by `RotatingCube`. Three classes deleted, one renamed, and the base file got cleaner instead of more cluttered.

### SoundEvent renamed to Sound

The `SoundEvent` enum had been misnamed since the beginning. It's not an event — it's the sound itself. You play a `Sound`, not a `SoundEvent`. The rename to `Sound` was mechanical and complete, touching every game file. The one exception: the values stay `ALL_CAPS` (`LEVEL_COMPLETE`, `SHOOT`, `TICK`) because the WAV filenames demand it. No other enum got that exception. We formalised the naming rules on the spot: constants are `ALL_CAPS` (`MIN_SPEED`), internal‑state enums are `ALL_CAPS` (`State.IDLE`, `Fruit.Apple`), and user‑facing enums are `PascalCase` (`Input.ButtonA`, `Alignment.Center`). The rules are clear, and the codebase now follows them everywhere.

### Colour model finalised

The colour model got its final resolution. `Colors.None` had been a problem since the May 18th transparency refactor — it tried to make transparency a colour, which is nonsense. A colour is pure RGB, `0xRRGGBB`. A pixel can be transparent, but that's a pixel property, not a colour property. We killed `Colors.None` completely. The canvas — `Game.pixels` — is always opaque, typed as `Array<Int>`, never nullable. Display‑object buffers remain `Array<Null<Int>>`, where `null` means "don't draw here." In C++, the same semantics will use the alpha byte: `0xFFRRGGBB` for opaque pixels, `0x00000000` for transparent. Colour constants stay as `0x00RRGGBB`. The two languages express the same idea with their own natural tools, and the mapping is direct.

### Input system

The input system was the session's major architectural addition. Since the earliest prototypes, games had been hardcoding `buttonPress(0)`, `buttonPress(1)`, `buttonPress(2)` — raw magic numbers that meant nothing. The C++ side already had a proper `Signal` enum from the hardware documentation, with 27 named inputs covering every possible controller configuration: four directional axes, a dozen buttons, three encoders, action triggers. The full spaceship controller spec, future‑proofed. We brought that into Haxe as `Input`, a `@:expose class` with static integer constants matching the signal IDs exactly. `Input.ButtonA = 9`, `Input.ButtonB = 10`, `Input.ButtonC = 11`, `Input.ButtonD = 12`. All 27 entries, even though the games currently use only three or four. They're there, silently, with their correct IDs, waiting for the hardware that will need them.

### Platform abstraction: System, Clock, Strip

Then came the platform abstraction that makes the whole thing portable. Haxe had `extern class Audio` already — the pattern was proven. We extended it to every platform‑specific service. `extern class Clock` provides `time:Float` and `update():Void`. `extern class Strip` provides `begin():Void` and `update():Void`, with a back‑reference `game:Game` so it can read `game.pixels`. And a plain Haxe `System` class wraps all three together. The `Game` constructor now takes a single `system:System` parameter instead of an `Audio` object. Inside, it wires `system.audio.game = this`, conditionally wires `system.strip.game = this`, and uses `system.clock.update()` / `system.clock.time` where `haxe.Timer.stamp()` used to be. The `Game` class no longer makes a single direct platform call. It is pure, portable engine code.

### All eleven games updated

All eleven games were updated. The pattern was mechanical and the same for every file: change the constructor from `(audio:Audio, resolution:Int)` to `(system:System, resolution:Int)`, call `super("GameName", resolution, system)`, and replace every `case 0:` with `case Input.ButtonA:`, every `case 1:` with `case Input.ButtonB:`, and so on. No game logic changed. Stack still shoots red/green/blue bullets with the same three buttons. Race still boosts Player A and Player B with the first and third buttons. SimonSays still maps four colours to four buttons. Slots still spins on a single press. Dino dropped its manual delta calculation in favour of the inherited `Game.delta`. Every game plays exactly as it did before, but now the button values are named, self‑documenting, and consistent across the entire platform.

### JavaScript host rebuilt

The JavaScript host was rebuilt to match. `SoundEvent` became `Sound`. The `Audio` constructor now takes `game` instead of `app`. A new `Clock` class wraps `Date.now() / 1000`. `Strip` and `Strip3D` gained empty `begin()` methods. The `GameController` creates `Audio`, `Clock`, and `Strip` instances, assembles a `System`, and passes it to the game constructor. The ad‑hoc `ButtonType` mapping object was deleted — buttons now carry their `Input` integer directly, and the keyboard keys 1‑4 map to `Input.ButtonA` through `Input.ButtonD`. No magic numbers in the host either.

### C++ architecture designed

The C++ architecture was designed in parallel but not implemented — that's for another session. We settled every translation detail: the `System` struct holding `Audio*`, `Clock*`, and `Strip*`; the ARGB pixel model with `0xFF000000` as the opaque flag; the `Input` enum matching the Haxe IDs; the module split into `Game.h`/`.cpp` (pure engine), `Hardware.h`/`.cpp` (Strip, Audio), and `Input.h`/`.cpp` (Switch, Encoder, Controller). The quirk list is documented: C++ `switch` needs `break` where Haxe breaks by default; deferred callbacks need a trampoline or action queue; virtual methods for `loop()` and `buttonPress()`; `millis()/1000.0f` for timing; memory management without a garbage collector. Nothing is unknown or undecided.

### Remaining items

A few small items remain: the Maze player still calls `haxe.Timer.stamp()` instead of using the game clock — the last direct platform call outside `Game.loop()`. `Synth.hx` is dead code, a dormant file from the May 17th audio work that nothing imports. The `Alignment` and `EdgeMode` enums are still `ALL_CAPS` while the naming convention says they should be `PascalCase`. And `game.js` currently hardcodes `[9,10,11,12]` for the button values, but with the new `@:expose class Input` generating a global JS object, it can use `[Input.ButtonA, Input.ButtonB, Input.ButtonC, Input.ButtonD]` directly. All minor, none blocking.

### Outcome

The session started with a codebase full of accumulated compromises — the App/Game split, the old DisplayObject, the missing input abstraction, the platform‑specific time calls leaking into the engine, the ButtonType junk in JavaScript, the Colors.None fallacy. It ended with a clean, unified, 71 KB platform that compiles eleven games from a single source of truth and has a direct, unambiguous path to C++. Every abstraction earned its place, every name says what it means, and the engine is genuinely portable for the first time. The chainsaw worked.
