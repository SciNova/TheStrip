# 17 May 2026 (b) – DeepSeek 3 – Slots rebuilt: new fruit set, wheel physics, DisplayObject integration, jackpot win

Slots rebuilt from scratch to align with the platform’s current architecture. The old game was a prototype with a hard‑coded 7‑fruit set, exponential deceleration tied to frame rate, and a redundant `Stopping` state; it was never integrated with the `DisplayObject` rendering pipeline.

The rebuild started with a blank slate and a list of non‑negotiable design rules: each wheel stops only at exact symbol centres (the “snap”), the physics are deterministic and frame‑rate independent, and every wheel is a `DisplayObject` filling its own pixel buffer.

### Fruit system

Nine fruits defined in an enum (`Apple`, `Banana`, `Grape`, `Orange`, `Cherry`, `Lemon`, `Watermelon`, `Blackberry`, `Strawberry`), each with a dedicated colour constant added to `Colors` (e.g. `Colors.Banana = 0xFFCC00`). A parallel `FruitSize` array gives each fruit a relative size (0.2–0.8), which determines the angular span on the reel. The fruit colours are used directly in the rendering switch – no helper functions, no indirection.

### Wheel mechanics

Each `Wheel` stores its rotation as a float in symbol‑index units (`[0, NUM_SYMBOLS)`), so integer values mean a symbol centre is exactly at the payline. Speed is in symbols per second. When the player presses the button, every wheel gets a random initial speed (`MIN_SPEED`–`MAX_SPEED`) and a random spin duration (`MIN_SPIN_DURATION`–`MAX_SPIN_DURATION`). The wheel runs at constant speed until its duration expires, then decelerates linearly using a single `DECELERATION` constant (15 symbols/s²). When speed reaches zero – capped, never negative – the rotation snaps to the nearest integer (`Math.round(rotation)`), guaranteeing a symbol centre lands on the payline. The deceleration is time‑based, so the stop feels identical at any frame rate.

### State machine

The game states are `IDLE`, `SPINNING`, and `RESULT`. `Stopping` is eliminated; deceleration is simply part of `SPINNING`. When all wheels have zero speed, the state transitions to `RESULT`. There the three centre symbols are compared: if all three match, `LEVEL_COMPLETE` plays; otherwise `LEVEL_FAIL`. After a 4‑second defer, the game returns to `IDLE`. The win condition is deliberately simple – jackpot only – leaving tiered wins (colour match, size match, pair) for a future iteration.

### DisplayObject pipeline

`Wheel` extends `DisplayObject` with `Alignment.CENTER`. Each wheel’s pixel buffer is the odd‑width segment it occupies on the strip. The cylinder rendering (parabolic brightness, fruit colours, silver background) is computed inside `Wheel.update()` and written directly to the local buffer. `Slots.render()` simply clears the canvas, calls `wheel.render()` for each wheel (which blits via the standard pipeline), and draws a luminance‑corrected white payline marker at each wheel’s centre pixel. This is the same pattern used by `Dot` and `Bullet` in Stack – every visible object owns its pixels and the main canvas is just a composite.

### Sound

A `TICK` sound fires every time a wheel’s rotation crosses an integer boundary, giving the classic mechanical reel feel. The tick was made functional by finally bridging the Haxe‑JS sound enum gap (carried over from the previous session’s audio work). Outcome sounds use the same `LEVEL_COMPLETE`/`LEVEL_FAIL` events as all other games, with the same 4‑second defer before returning to idle.

### Outcome

The game is fully playable. The three wheels have fixed, pre‑randomised symbol layouts (8 symbols per wheel, 5 distinct fruits with controlled repeats) to guarantee a balanced visual rhythm and a jackpot probability of roughly 5%. The rendering is correct, the snap aligns perfectly, and the independent stop times create the natural staggered‑stop tension of a physical slot machine. The only non‑game issue remaining is the platform‑wide luminance correction being too aggressive, which affects all games equally and will be tuned later.
