# 13 Jun 2026 – DeepSeek 3 Expert – The C platform unified, five games ported, and the Python reference back‑propagated

The session opened with a chainsaw in one hand and a vacuum cleaner in the other. The C platform had been through a brutal refactoring in the days prior — pure C, single‑header, manual OOP — and the code was correct, but the names were a mess. `ctrl`, `ev`, `be`, `sys`. Abbreviations that had no place in a codebase that prided itself on being human‑readable. The plan was simple: clean the naming, extract the hardware layer, and call it done. Instead, the session folded in on itself. Mid‑stream, the entire platform was paused, a Python reference implementation was built from scratch in a terminal, the event system was redesigned at the bit level, and only then — hours later — did the C side receive its final form. The result is a single header, `rgbstrip.h`, that mirrors the Python reference byte‑for‑byte, a `hardware.h` that isolates every physical detail, and five games updated to a unified `InputEvent` that requires no casts, no type‑checking, and no hidden conventions. The session was not a refactoring. It was a proof that the platform’s design is now independent of any language.

### The naming war

The C code worked. But it was littered with abbreviations that violated the platform’s own standard. `ctrl` instead of `controller`. `ev` instead of `event`. `be` for `buttonEvent`. The `DebouncedPin` functions used `dp`. The `System` functions used `sys`. Every struct’s “method” parameter was the generic `self`. The cleanup was mechanical but total: every function now carries the struct name as a prefix (`Button_process`, `Encoder_update`, `System_handleInput`), every parameter is the full struct name (`Button* button`, `Controller* controller`), and the `self` pointer was replaced by the specific type name across every file. `DebouncedPin` became `pin`. `System` became `system`. The entire codebase now reads like typed OOP with an underscore instead of a dot.

The rule was formalised during the session: single‑letter variables are acceptable for short‑lived temporary values (`i`, `r`, `g`, `b`), but anything that persists across more than a few lines must be a full word. No abbreviations, no “Elon Musk kid names.” The platform’s names are now so transparent that a non‑programmer could read `Game_clear(&game->super)` and understand what it does.

### Hardware extraction

The `hardware.h` file was born in this session. Every physical detail that had been cluttering the sketch — pin definitions, `pinMode` calls, `digitalRead` loops, the GRB conversion buffer, the `ws2812b_write` call, the 80 µs reset pulse, even the Wokwi‑specific 1 ms frame cap — was moved into a single header. Two structs, `StripView` and `Input`, with `_init` and `_update` methods, became the complete I/O layer. The sketch collapsed to five active lines: `System_init`, `Input_init`, `StripView_init`, and a three‑line `loop()` that calls `System_loop`, `Input_update`, and `StripView_update`. No pin numbers, no `#define` clutter, no hardware knowledge survives in the sketch.

A development escape hatch, `hardware-dev.h`, was also created. It replaces the hand‑tuned assembly driver with the Adafruit NeoPixel library, using a plain `new Adafruit_NeoPixel(...)` pointer. On a real 16 MHz Arduino Uno, this driver works immediately — the strip displays correct colours, every game plays identically, and the only cost is ~370 bytes of SRAM. The 16 MHz assembly driver remains a known frontier; the Adafruit driver is the pragmatic workaround that makes real‑hardware testing possible today.

### The Python detour

Mid‑session, the work paused. A separate Python session — logged independently as the 13 Jun 2026 Python reference entry — built `rgbstrip.py`, a complete, dependency‑free console that runs fourteen games in an ANSI‑colour terminal. That session killed Haxe as the canonical reference, unified the event system into a single `Action` integer with a clean bit‑level layout (press/release pairs, encoder actions, system buttons in block 3, the `is_game_button_press` helper), and proved that the platform’s architecture is cleaner when expressed in a language that doesn’t fight back.

The Python session occurred chronologically inside this C session. When it completed, the C side was updated to match. The event system redesign — the single most important architectural change — was back‑propagated from Python to C with zero design changes. The Python reference served as the flawless blueprint; the C translation was mechanical and completed in minutes.

### The event‑system unification in C

The old C event hierarchy — `InputEvent`, `ButtonEvent`, `EncoderEvent`, `InputEventType`, `ButtonEventType`, three separate structs, manual casts — was killed. It was replaced by a single `InputEvent` struct containing only `Action action` and `float value`. The `Action` enum now carries press/release pairs for every button (e.g., `A_PRESS = 0xC1`, `A_RELEASE = 0x81`, with `A_ACTION = 0xC1` as the legacy alias), encoder actions (`ENCODER_LEFT = 0x01`, `ENCODER_RIGHT = 0x02`, `ENCODER2_LEFT = 0x03`, `ENCODER2_RIGHT = 0x04`), and system buttons (`PAUSE_PRESS = 0xD8`, `MENU_PRESS = 0xD9`, `POWER_PRESS = 0xDA`). The bit‑level layout — bit 7 = press, bit 6 reserved for hold, bit 5 = button flag, bits 4‑3 = block selector, bits 2‑0 = device index — is implemented but never exposed to games. A single static inline function, `Action_isGameButtonPress`, answers the universal “did the user push something?” question.

`Button` now stores two actions (`pressAction`, `releaseAction`) and `Button_process` emits the correct one on each edge. `Encoder` stores its own `leftAction` and `rightAction` and sets `event->action` directly — the caller no longer stamps the action after the fact. `Controller_init` wires every button with its press/release pair. `System_handleInput` checks two exact constants (`MENU_PRESS`, `PAUSE_PRESS`) and forwards everything else to the game with a flat `event->action` switch. No event‑type branching, no casts, no `super.action` stamping in the scanner.

`hsv_to_rgb` was added to the kernel, matching the Python implementation exactly. `ColorLight` now calls it directly instead of using its own local version.

### The five games updated

All five existing C games were updated to the new API. The pattern was identical in every file: include `rgbstrip.h` instead of `strip.h`, change the `handleInput` function signature to take `InputEvent* event` instead of the old `InputEvent* ev`, and replace the old `if (ev->eventType == BUTTON_INPUT_EVENT) { ButtonEvent* buttonEvent = (ButtonEvent*)ev; … }` with a flat `switch (event->action)`. No game logic changed.

- **ColorLight** — now uses `FIRE_PRESS`/`B_PRESS` for level toggle, `FIRE2_PRESS` for mode toggle, `A_PRESS`/`DOWN_PRESS` for level down, `C_PRESS`/`UP_PRESS` for level up, `LEFT_PRESS`/`RIGHT_PRESS` for mode adjust, and `ENCODER_LEFT`/`ENCODER_RIGHT`/`ENCODER2_LEFT`/`ENCODER2_RIGHT` for encoder control. The local `hsvToRgb` function was replaced by the kernel’s `hsv_to_rgb`.
- **Moodlight** — `A_PRESS` increases speed, `B_PRESS` cycles themes, `C_PRESS` decreases speed.
- **WhiteLight** — `FIRE_PRESS`/`FIRE2_PRESS`/`B_PRESS` toggles fade, `A_PRESS`/`DOWN_PRESS`/`LEFT_PRESS`/`ENCODER_LEFT` decreases brightness, `C_PRESS`/`UP_PRESS`/`RIGHT_PRESS`/`ENCODER_RIGHT` increases brightness.
- **SimonSays** — `A_PRESS` through `D_PRESS` map to the four colours. The event‑type check and `BUTTON_PRESS` guard are gone; the action switch alone handles validation.
- **FlappyBird** — uses `Action_isGameButtonPress(event->action)` to accept any button as the flap trigger. The explicit `BUTTON_INPUT_EVENT` check is gone.

### The sketch

The sketch was updated to match. It now includes `hardware-dev.h` for the Adafruit driver on real hardware, or `hardware.h` for the assembly driver in simulation. Game switching is done by commenting out the active game’s init block and uncommenting another — exactly the same pattern as before, but with the new `*_init` function signatures.

### The 16 MHz assembly driver

The 16 MHz bit‑bang driver was chased for a significant portion of the session. The core discovery — confirmed by an old hand‑calculated comment in the assembly file — was that the correct timing is 19 cycles per bit (odd), not 20. The 8 MHz original uses 11 cycles per bit, which is already slightly longer than the nominal 1.25 µs period. The 16 MHz translation requires 19 cycles with specific NOP placements: one branch gets 1 NOP in the high phase and 7 in the low; the other gets 2 NOPs in the high and 6 in the low. Despite getting the NOP counts correct, the driver failed to produce a clean image on the Wokwi simulator — likely due to the well‑known mismatch between `F_CPU` (16 MHz for the Uno) and the simulation clock (8 MHz when `"frequency": "8m"` is set in `diagram.json`, or 16 MHz when it is omitted). With the Adafruit driver providing a stable fallback, the assembly driver work was paused. It will be validated on real hardware where the clock is unambiguous.

### The outer session completed

The session ended where it began: with a clean, working C platform. But it had travelled through a Python revolution in the middle, and the C side emerged carrying every improvement that revolution produced. The platform now has two living implementations — Python and C — that are logic‑for‑logic identical. The Python reference is the canonical specification. The C platform is the hardware implementation. Both use the same event system, the same naming conventions, the same class hierarchy, and the same game logic.

The Haxe transpiler, which had been the source of truth since the platform’s earliest days, is now frozen. It still serves the web simulator, but the platform no longer depends on it for design or validation. The terminal is the new development environment. The C header is the new hardware delivery vehicle.

### Remaining items

The 16 MHz assembly driver awaits validation on a real Arduino Uno at 16 MHz with a known clock. The `Pacman` and `Cars` games have not yet been ported to C; they exist in Python and can be tested in the terminal (with the acknowledged key‑release limitation) but await real hardware for full validation. The `Maze` game has not been ported to either Python or C. The menu system exists in the C kernel’s state machine (`SYSTEM_MENU_STATE`) but has no visual implementation beyond the `Strip_testPattern` placeholder. The `Synth.hx` audio engine remains dormant. None of these are regressions — they are the platform’s acknowledged frontier, and the Python reference is ready to lead the way for every future addition.
