### Gen 0 and Gen 1: the product line split

The session's foundational decision was the clean separation of the platform into two product lines that are not "versions" of each other but parallel families sharing one engine.

**Gen 0** is the wired, local, offline product line. It uses the `WiredController` class exclusively—buttons and encoders soldered directly to the strip's MCU pins, no radios, no BLE, no Wi‑Fi, no internet. The products are self‑contained: a dimmer with two encoders, a kids' console with two fixed gamepads, an e‑bike signaler with hardwired switches. Gen 0 is what ships to the Haredi community and what runs on an ATtiny.

**Gen 1** is the wireless, remote, BLE‑based product line. It does not use `WiredController` at all. Instead, `BTRemoteController`, `AppRemoteController`, `WebRemoteController`, `IRRemoteController`, and `CANRemoteController` handle input over various transports. The strip itself has no physical controller ports; all input arrives wirelessly. The web app is the keystone of Gen 1—a zero‑install, GitHub Pages‑hosted BLE controller that works on any Bluetooth browser without downloading anything.

The distinction is not "better" or "worse"—it's different products for different markets. The core engine (`system.h`, `graphics.h`, every game header) is identical across both lines. The split is purely in the transport layer: `hardware.h` defines the wired path; `bt.h` (later renamed `ble.h` after an Arduino header collision) defines the BLE path. A single sketch chooses which line it belongs to by including the appropriate headers and instantiating the appropriate controller classes.

The sketch naming convention was formalised: `wired-*` for Gen 0 products, `bt-*` for Gen 1. The current `sketch.ino` became `wired-console.ino`; a new `bt-console.ino` (later `ble-console.ino`) was created for the BLE test firmware.

### The BLE protocol: every byte specified

The entire BLE GATT interface was designed from scratch. The strip acts as a BLE Peripheral with one service and four characteristics:

- **Identity** (READ) — magic string (10 bytes), MAC (6), firmware version (2). Used by controllers to validate they're connected to a genuine Strip.
- **Command** (WRITE) — configuration commands: Lock, Unlock, Clear whitelist, Remove device.
- **Whitelist** (READ) — trusted device list for the app to manage.
- **Action** (WRITE) — direct game input from web apps and other Central‑only devices.

The controller (physical gamepad, native app) acts as a BLE Peripheral with two characteristics:

- **Identity** (READ) — magic string identifying the controller type (`"rgbctrl"`, `"rgbdimm"`, `"rgbapp "`, `"webapp"`).
- **Action** (NOTIFY) — button events pushed to the strip when it subscribes.

The web app is a special case: Web Bluetooth is Central‑only, so it cannot expose a GATT server. Instead, it connects to the strip and writes directly to the Strip's Action characteristic. This means the web app is a first‑class controller with a slightly different transport—write instead of notify—but the `Action` bytes are identical. The strip doesn't care how they arrived.

UUIDs were generated with a Python script and locked into constants shared across C, Python, and JavaScript. The `Action` enum values in JavaScript match the C `Action` enum byte‑for‑byte. Every SVG panel button carries `data-press` and `data-release` attributes with human‑readable action names that map directly to those bytes.

Pairing and security were fully specified: the strip has a single physical button for whitelist management (short press = lock, long press = unlock). Controllers have a dedicated BT button for cycling through available strips. The mobile app can manage the whitelist via the Command characteristic. The system supports a maximum of two simultaneous BLE connections, filling the lowest free port (0 or 1). The third connection is refused.

The Combined Menu/Power button was fully designed but deferred: the physical menu button uses hold detection—short release toggles menu/play, long hold powers off. The pause button remains a simple press button. This requires a new `Command` enum (`MENU_BUTTON_PRESS`, `PAUSE_BUTTON_PRESS`, `POWER_OFF`, `POWER_ON`) and a `HoldingButton` class with four event slots. The design is complete but unimplemented.

### The C++ BLE server: `ble.h`

A complete C++ BLE server was built and tested on real ESP32 hardware. The file was originally named `bt.h` but collided with an internal Arduino header—a classic Arduino namespace conflict that was solved by renaming to `ble.h`. The class `BT` became `BLE`, and all handlers followed: `BTHandler` → `BLEHandler`, `BTActionHandler` → `BLEActionHandler`, `BTCommandHandler` → `BLECommandHandler`.

The `BLE` class owns the `BLEServer`, the service, and all four characteristics. It stores a `System*` and a single `WebRemoteController*` (limited to one controller for now due to a known multi‑connection disconnect bug in Arduino core 1.0.3). The constructor takes a `System*` so the controller can route actions into the game engine.

The `WebRemoteController` class holds the port, connection ID, and a `BLE*` reference. Its `handleInput(actionByte)` method constructs an `InputEvent` and calls `System_handleInput(ble->system, port, &event)`. The `BLEActionHandler::onWrite` callback routes incoming bytes directly to the controller.

The C++ circular dependency problem was solved by the "header + implementation" pattern: class declarations with only method signatures at the top, the full `BLE` class definition in the middle, and all method implementations at the bottom after `BLE` is complete. This is the standard single‑file C++ pattern, functionally identical to a `.h` + `.cpp` split concatenated into one file.

A single‑controller limit was enforced in `BLEHandler::onConnect`: if `controller` is not `nullptr`, the new connection is immediately disconnected. Disconnection triggers `onDisconnect` which deletes the controller and sets the pointer to `nullptr`.

The firmware was tested with the web app on a real ESP32. The first connection works perfectly—actions are received and printed to serial. The second connection was attempted but failed due to Android's per‑peripheral BLE connection limit (two browsers on the same phone cannot connect simultaneously). A two‑phone test proved the BLE server can accept multiple connections, but the old core's `onDisconnect` misreports the connection ID when multiple clients are connected. This bug is documented and deferred until we upgrade to a modern ESP32 Arduino core.

### The web controller (JavaScript)

The `WebController` class in `strip.js` was built as the primary Gen 1 input device. It manages:

- **Panel loading** via Flask routes serving SVGs extracted from `panels.md`. The panels are later embedded directly into the page as a `svgs` JavaScript object, eliminating the Flask dependency for production.
- **Panel navigation** using `+` and `-` keys (`=` also works for `+` without Shift).
- **Keyboard input** mapped through `data-key` attributes on SVG elements: `1`–`4` for ABCD, `5`/`6` for Fire/Fire2, `ArrowUp`/`ArrowDown`/`ArrowLeft`/`ArrowRight` for directional buttons.
- **Pointer input** with `setPointerCapture` to fix missing release events on quick taps.
- **BLE connection** via `navigator.bluetooth.requestDevice` with a single "Connect" button.
- **Action transmission** via `writeValue` to the Strip's Action characteristic, using the `sendAction(action)` method.

The class mirrors the C++ `BLE` and `WebRemoteController` architecture: `handleInput(action)` calls `sendAction(action)` which writes the byte over BLE. The button press/release mapping uses the same `Action` enum byte values as the C firmware. The entire pipeline—SVG touch → Action byte → BLE write → ESP32 serial print—was tested and verified end‑to‑end.

The web app is the default Gen 1 controller. It requires zero install, works on any Bluetooth browser, and is always up‑to‑date because it's served from GitHub Pages. Physical controllers, native apps, and IR remotes are optional accessories. The strip ships as a complete product usable with nothing but a browser.

The Flask development server was configured to listen on `0.0.0.0` for multi‑device testing. A static `svgs.js` build step was designed but deferred until the GitHub Pages deployment.

### Python reference updates

The Python reference received structural surgery to match the new architecture:

- `rgbstrip.py` renamed to `system.py`. All game imports updated.
- `rgbstriplib.py` renamed to `graphics.py`.
- The `Controller` class was removed from `system.py`. The `System` class no longer owns a controller array. `System.handle_input` now takes `controller_id` (int) directly.
- `WiredController` was added to `hardware.py` as a reference class with the full button/encoder complement and an `emit(action)` method that calls `System.handle_input`.
- The `Action` enum was left untouched—it is the canonical reference, and the JavaScript/C implementations must match it.
- A long‑standing arrow‑key bug in `hardware.py` was fixed by removing the blocking `select` timeout from the escape sequence handler and replacing `sys.stdin.read(2)` with two sequential `sys.stdin.read(1)` calls.

### Hardware pin definitions and the landmine map

The session produced a definitive pin map for every target MCU. Platform‑specific constants—`LED`, `SPI_SCK`, `SPI_MOSI`, `SPI_MISO`, `SPI_CS`, `I2C_SCL`, `I2C_SDA`—are defined in three clean `#if` blocks in `hardware.h`. A `DISPLAY_DC` constant was added (‑1 for AVR, pin 4 for ESP32).

`STRIP_DATA` was unified to pin 3 across all platforms, moving it from pin 2 to free the built‑in LED on ESP32. The button pins shifted up to start from pin 4. A "landmine map" of unusable pins was documented for each platform, covering serial TX/RX, SPI, I²C, boot strapping pins, and the built‑in LED conflict on Uno.

The display will use the standard SPI constants directly—the `Display` class knows nothing about specific pin numbers, only `SPI_SCK`, `SPI_MOSI`, `SPI_CS`, and `DISPLAY_DC`.

### Display classes

Two LCD display driver classes were built in C++ using the Adafruit library: `DisplayILI9341` and `DisplayST7735`. Both take a `System*`, initialise the hardware in `begin()`, and provide an `update()` method that reads `system->strip.pixels` and renders a horizontally centred, 1‑pixel‑high line of coloured dots on the LCD. The 24‑bit RGB colours are converted to 16‑bit 565 before drawing. Each strip pixel maps exactly to one LCD pixel.

The classes live in `hardware-dev.h` alongside the existing `AdafruitStripView`. They follow the same pattern as `StripView`—output drivers that read from the strip buffer and render on physical hardware, with no changes to the game engine.

The system and games never touch the LCD directly. The `Display` class is a system‑level output device with its own API, suitable for menus and status information in future iterations. For now, it's a development convenience that mirrors the strip output on a breadboard‑friendly screen.

### Code style and naming conventions

The session formalised several style rules through practice:

- `#if`/`#endif` directives are indented to match the code block they control. The outer `#ifndef` guard stays at column 0. Inner directives display purple in mcedit, visually distinguishing them from the red top‑level defines and includes. This is the modern C standard and matches the Linux kernel style.
- The `switch` case exception: the three RGB assignment statements can share a single line (`r = v; g = t; b = p;`), but `case` and `break` each get their own line.
- `Button_process`, `Encoder_process` (renamed from `Encoder_update`), `Game_loop`, `System_loop`, `WiredController_loop`, `StripView_update`—the naming is now perfectly consistent: `_process` for input state machines, `_loop` for game/system orchestration, `_update` for visual refresh.
- All game header files renamed to match Python: `Moodlight.h`, `ColorLight.h`, etc.
- Single‑letter variables (`r`, `g`, `b`) are acceptable for short‑lived temporaries. Everything else uses full words.

### The session's character

This was the session where the platform's scale became undeniable. The BLE stack alone—before any game logic—consumes 931 KB of flash and 35 KB of RAM on ESP32. The wired path compiles on an ATmega328P with room to spare. The split between the lean core and the fat BLE transport is not a design choice; it's a physical necessity imposed by the protocol stack. The architecture proved itself by accommodating both extremes without a single `#ifdef` in the game logic.

The ArduinoDroid environment was exposed as a dead end for BLE development—its bundled core 1.0.3 cannot be updated, its `BLEServer` lacks `setMaxConnections`, its disconnect callbacks lie about connection IDs. The path forward is `arduino-cli` with a modern core, or the ESP-IDF directly.

The session was long, chaotic, and frequently derailed by naming conflicts, circular dependencies, and the assistant's tendency to over‑engineer. But every wrong turn was corrected, every bad abstraction killed, and every name forced to earn its place. The platform emerged coherent, self‑documenting, and genuinely portable across transports, languages, and hardware scales. The chainsaw got a workout. The MOAB stayed in its silo. The work was honest.
