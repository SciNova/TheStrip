# 4 Jun 2026 – DeepSeek 3 Expert – C++ translation, Stack on hardware, and the missing‑limb tango

The session began as an experiment: take the Haxe reference platform, translate it to C++, and see if a real game — Stack — could run on an Arduino. It ended with a fully playable Stack on a simulated Mega, a catalogue of C++‑imposed workarounds, and a hard‑earned understanding of every broken layer in the embedded toolchain. The entire C++ core, the game logic, the rendering pipeline, and the system state machine were built from scratch, debugged through serial‑out and Wokwi glitches, and finally stabilised. This was not a port. It was a forced march through a minefield of missing features, incomplete simulators, and the stubborn refusal to let any of them win.

### The translation philosophy

The platform was translated line‑for‑line, preserving every class name, member name, and behavioural contract from the Haxe reference. No getters, no setters, no hidden virtual dispatch, no constructors that did more than assign fields. The `Game` class holds a direct `uint32_t* pixels` pointer into the `Strip` buffer — no accessor, no indirection. The `Shape` class stores its local buffer as ARGB, with `0xFF000000` as the opaque marker and `0x00000000` as transparent, a direct mapping of Haxe’s `Null<Int>`. The `Colors` constants are `static constexpr uint32_t`, the same packed RGB values used everywhere.

Where C++ forced a deviation from the clean design, the deviation was isolated and named with a `CPP_` prefix. `CPP_InputHandler` and `CPP_object` exist because C++ cannot pass a non‑static member function as a plain function pointer; the same pattern that every other language handles with automatic `this` binding requires a static trampoline and a `void*` context in C++. `CPP_handleInput` is the single free function that bridges the gap. The `Button` constructor stores both the trampoline and the object pointer, exactly mirroring the workaround already accepted for the platform’s input system. A default constructor was added to `Button` solely because `Controller` stores buttons as value members — necessary to avoid heap‑allocating 32 individual buttons that would exhaust the Uno’s SRAM — and C++ refuses to construct member objects without a default constructor or an initializer list. The initializer list itself is used only where absolutely unavoidable: calling a parent constructor with arguments. Every other member assignment is done as `this->x = x` in the constructor body.

No new files were created. Every class lives in the minimal set of `.h`/`.cpp` pairs that already existed. The circular‑include problem between `Input.h` and `System.h` was solved by forward‑declaring `Clock` in `Input.h` and changing the `Button` member from `Clock&` to `Clock*` — a one‑character change in the access syntax (`clock->time` instead of `clock.time`) that completely broke the dependency cycle without adding any files.

### The Action enum and InputEvent hierarchy

The `Action` enum uses `1UL << N` for every value, a necessary concession to AVR’s 16‑bit `int`. Without the `UL` suffix, `1 << 30` and `1 << 31` overflow a signed 16‑bit type and produce compiler warnings. With `UL`, the shifts are well‑defined and the bitmask values are exactly what the Haxe reference specifies. The clean `InputHandler` typedef — `void (*)(InputEvent&)` — sits in the header as unused documentation of the ideal callback signature that C++ cannot support for member functions.

The `InputEvent` hierarchy mirrors Haxe exactly: a base class holding `Action action`, with `ButtonEvent` and `EncoderEvent` as subclasses carrying their respective event‑type enums. Because Arduino builds with RTTI disabled, `dynamic_cast` is unavailable. Instead, a small `InputEventType` enum — `Button`, `Encoder` — is stored directly in `InputEvent` and set by each subclass constructor. A simple `if (event.eventType != InputEventType::Button)` replaces the missing cast, adding exactly one enum and one field, with zero virtual‑method overhead.

### The System state machine

A parallel session refined the `System` state machine into three states: `MENU`, `PLAY`, and `TEST`. The Menu button toggles between `MENU` (freezes the game — `loop()` is simply not called) and `PLAY`. The Pause button is contextual: in `PLAY` it calls `game->togglePause()`; in `MENU` it enters `TEST` mode and fills the strip with `testPattern()`; in `TEST` it returns to `MENU`. All of this is driven by `Press` events only, filtered early in `handleInput`. No `previousState` variable, no `paused` flag, no early returns — the state machine itself is the only source of truth.

Time freeze is handled in `System::loop()`. When the game is in `GameState::PAUSED`, `delta` is set to zero so that the game’s own `loop()` still runs and still renders, but all time‑dependent logic sees no progression. In `MENU`, the game’s `loop()` is skipped entirely, freezing the last frame on the strip. The `TEST` state also skips the game loop, so the diagnostic pattern stays static. All three behaviours fall out of the state machine without any extra timers or flags.

### The NeoPixel driver: a four‑way battle

The session spent hours on what should have been a simple problem: pushing 120 pixels to a WS2812B strip. The original `ws2812b.S` — a cycle‑accurate 8 MHz assembly driver with dynamic pin‑to‑port mapping — had been proven on the ATtiny85 in Wokwi. It used a base address of `0x32` for port calculation, correct for the ATtiny’s memory layout. Porting it to the Arduino Uno at 16 MHz required re‑timing the inner loop from 10 cycles per bit to 20 cycles per bit. Multiple versions were attempted, each failing: the timing was either slightly off (producing solid colours instead of gradients) or the pin‑mapping for `PORTD` at address `0x2B` clashed with the ATtiny‑tuned calculation. After a dozen iterations, the custom driver was shelved for simulation purposes.

The Adafruit NeoPixel library — a known‑good, battle‑tested 16 MHz implementation — was brought in as a temporary renderer. It worked immediately. The test pattern displayed correct gradients. Stack rendered correctly. The library was kept as the V1 simulation renderer, with the understanding that it adds roughly 360 bytes of SRAM overhead (its internal pixel buffer duplicates the platform’s own buffer) and is not the final hardware path.

A final attempt was made to return to the custom driver on the Arduino Mega, where the 8 KB SRAM would make the Adafruit overhead irrelevant. The Mega’s pin‑12 — PORTB, bit 6 — required either a different encoded value passed to the dynamic driver (`0x16`, which worked for port selection but not for the base‑address calculation) or a hardcoded driver variant. The base address in the assembly (`0x32`) was designed for the ATtiny; changing it to `0x1F` produced the correct Mega PORTB address (`0x25`), but the Mega’s simulation in Wokwi does not support the `frequency` attribute, leaving it locked at 16 MHz while the custom driver was timed for 8 MHz. With no way to change the clock and no way to test the driver at 16 MHz on the Mega’s port layout, the custom driver was abandoned for the simulation phase. The Adafruit library remains the renderer on the Mega.

The conclusion is blunt: the custom assembly driver is correct for a real ATtiny85 or ATmega at a known clock speed, but Wokwi’s inability to simulate timer peripherals or change the Mega’s clock makes it untestable in that environment. The driver will be validated on real hardware. For now, the Adafruit library provides a stable, correct rendering pipeline.

### Memory: the Uno’s 2 KB wall

The compiled binary for the Uno is 14.6 KB of flash and 326 bytes of static data — the code fits comfortably. The problem is SRAM. The `System` contains two `Controller` objects, each with 16 `Button` value members. Each `Button` holds several `float` timestamps, a `Clock*`, a function pointer, and a `void*`, consuming roughly 20 bytes. The 32 buttons alone consume about 640 bytes. The `Strip` buffer is 480 bytes (120 × `uint32_t`). The Adafruit library allocates an additional 360‑byte internal buffer. The Stack game dynamically allocates `Dot` and `Bullet` objects on the heap. The Arduino runtime, the `Serial` buffer, and the stack consume the rest. The total exceeds the Uno’s 2 KB SRAM, and the heap‑stack collision causes the game to either never start or crash silently.

Switching to the Arduino Mega with 8 KB SRAM resolved the issue completely. The game runs stably with all 12 buttons and the full 120‑pixel strip. No code changes were required. The Mega is the baseline target for the simulation; the Uno remains viable for simpler games (Moodlight, SimonSays) or for a version of Stack that reduces `MAX_RESOLUTION` and uses the custom driver to eliminate the Adafruit overhead.

### Stack: from Haxe to C++

The entire `Stack.hx` game was translated into `Stack.h` and `Stack.cpp`. The class hierarchy — `Dot`, `Bullet`, `Snake`, `Stack` — and every game‑logic detail are preserved exactly. The snake movement, bullet physics, colour matching, explosion animation, and level progression all work identically to the Haxe version.

Two changes were required from the Haxe design. First, the `defer(playLevel, 4)` pattern was replaced by a simple `delay(float seconds)` method on `Game`. The game’s `loop()` decrements `delayTime` by `system->delta` and returns early while it is non‑zero; when it reaches zero, the game checks a `StackStage` enum (`PLAY`, `LEVEL_FAIL`, `LEVEL_COMPLETE`, `GAME_COMPLETE`) to decide what to do next. This eliminated the need for the C++ member‑function‑pointer trampoline that `defer` would have required at every call site. The `delay` mechanism is a single float and a single check, with zero platform changes beyond the `delayTime` member already present in `Game`.

Second, a critical 16‑bit shift bug was discovered and fixed. The bullet trail and explosion rendering packed colour components with expressions like `(rr << 16) | (gg << 8) | bb`. On AVR, `int` is 16 bits wide, and shifting a 16‑bit value by 16 is undefined behaviour in C++. The compiler produced garbage for the red and green channels: the green bullet appeared yellow (red and green both active), and the red bullet was invisible (the red channel was zeroed). The fix was to explicitly cast each component to `uint32_t` before shifting: `(((uint32_t)rr << 16) | ((uint32_t)gg << 8) | (uint32_t)bb)`. After this change, all three bullet colours rendered correctly. The same fix was applied to the `Dot` explosion rendering, which had the same latent bug.

The snake’s initial position was also adjusted. In Haxe, the snake starts off‑screen (position = resolution) and creeps into view over several seconds. In C++, `Snake::build` sets `position = game->resolution - length()`, placing the first dot at the visible edge of the strip immediately. This makes the game start instantly rather than after a confusing 10‑second delay.

### Wokwi: the simulator as adversary

The Wokwi simulation environment caused more problems than it solved. Its visual editor repeatedly corrupted the wiring diagram, adding invisible short‑circuits between adjacent button pins, misplacing the strip, and creating phantom connections that survived JSON edits. The green button appeared stuck because an invisible wire tied its pin to the red button’s pin; the red button fired continuously because its pin was permanently pulled LOW by the same short. Several hours were lost debugging problems that did not exist in the C++ code.

The only reliable workaround was to strip all custom routing strings from the `diagram.json` — replacing every `[ "v-22", "h-140", "*", "v0" ]` with empty arrays `[]` — and to hard‑refresh the page to clear cached wiring state. After that, the buttons behaved correctly.

Wokwi also does not support the `frequency` attribute on the Arduino Mega, does not simulate advanced timer peripherals (input capture, PWM input mode), and does not allow the NeoPixel canvas to be driven by a pin on PORTB via the custom assembly driver without additional external components. It is a useful NeoPixel renderer but an unreliable circuit simulator. Every hardware‑related bug in this session was ultimately traced to the simulator, not to the platform code.

### The missing‑limb pattern

Every piece of the toolchain proved to have a critical, known‑for‑decades gap. C++ cannot bind a member function to a plain function pointer. Haxe drops enums from JavaScript output. The Arduino Mega’s pin‑to‑port mapping differs from the Uno’s. Wokwi corrupts wiring visually and lacks timer simulation. The WS2812B uses GRB colour order because of a 15‑year‑old chip design decision that nobody ever fixed. Every layer is missing something that every other layer considers basic. The platform’s `CPP_` markers are the honest response: each workaround is a labelled scar, not a hidden compromise, and the clean design is always visible right next to it.

### Remaining items

The debug `Serial.print` statements in `Stack::handleInput` — added during the bullet‑colour investigation — need removal. The `static inline float` members in `Stack.h` should become `static constexpr float` for compatibility with older compilers; Wokwi’s newer toolchain accepts `inline`, but local Arduino builds may not. The `menuPattern()` method is a placeholder that lights a single white pixel. The `Colors::correctLuminance` function is bypassed with an early `return color`; it can be re‑enabled when the rendering pipeline no longer uses the Adafruit library. The custom AVR assembly driver awaits validation on real hardware, where the clock speed and port layout can be controlled directly.

### Outcome

The C++ platform core is a faithful, line‑for‑line translation of the Haxe reference. Stack is a fully playable, visually correct game running on a simulated Arduino Mega with 120 pixels and 12 physical buttons. Every C++‑imposed workaround is isolated under a `CPP_` label. The system state machine provides MENU, PLAY, and TEST modes with contextual button behaviour, all without extra variables. The session is a self‑contained milestone: a working game on (simulated) hardware, achieved through a multi‑hour gauntlet of debugging, refactoring, and refusing to let broken tools win.
