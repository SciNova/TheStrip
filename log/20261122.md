# 22 Nov 2026 – Claude Sonnet 5 – DemoScene synced to a real track, a loop-wrap audio bug fixed, and the audio engine's own sense of time corrected

We wired `DemoScene` to the same MOD track `Test.js` already proved out, worked out how its stage cycling should actually line up with the music, found and fixed a real bug in how a looping `Tracker` handles its own seam, then spent most of the session chasing what first looked like an `Analyzer`/FFT design question and turned out to be a real correctness problem in how the audio engine measures time — settled by giving the audio render path its own self-advancing `audio.timestamp`, with no dependency on the system clock at all.

### DemoScene: loading the track, driving stages off its own structure

`DemoScene` got its own `Tracker`, loading `faggots_universe.mod` the same way `Test.js` does, and the existing time-based stage cycling (`STAGE_DURATIONS`, one of ten `Stage`s held for a fixed number of seconds) was replaced with cycling driven by the track's own position instead. We inspected the actual file rather than guessing: 27 segments, each exactly one bar (64 rows), order table `[4,5,6,0, 7,8,10,11, 9,9,6,0, 10,11,9,9, 6,0,15,16, 18,20,17,17, 12,13,21]`. Grouped from the start in blocks of 4, this splits with no remainder into six clean 4-segment blocks (24 bars) plus a 3-segment tail — confirmed as a real 3-bar outro, not noise, since those last three patterns (12, 13, 21) are each used nowhere else in the order table, unlike every earlier pattern. Decision: loop only the first 24 segments (`tracker.play(0, 0, 24, true)`), skip the outro, and use `tracker.segment` directly as the bar index for picking a stage slot (`Math.floor(segment / BARS_PER_SLOT) % stageCount`) — no need for `tracker.bar`, which only reports bar-within-segment here since every segment already is one bar.

Which of the ten existing stages to keep was worked out by going through them one at a time: `FIREWORKS`, `AURORA_BOREALIS`, `COPPER_BARS`, `SCANNER`, `REACTIVE_BURST`, `BOUNCING_BALLS` kept; `FRACTAL_MOUNTAIN`, `STARFIELD_WARP`, `DIGITAL_RAIN` dropped as weak on their own merits; `INTERFERENCE` dropped last, judged the most generic-plasma-looking of the set once `SCANNER`/`COPPER_BARS` were already covering similar moving-bar territory with more visual craft. That left exactly six — matching six slots. First attempt used `BARS_PER_SLOT = 4` (one slot per 4-bar block, 6 slots across the 24-bar loop); corrected to `BARS_PER_SLOT = 2` once the math was rechecked, so the six-stage cycle runs twice per loop instead of once. No existing render function, helper, or class for any of the ten stages (kept or dropped) was touched or removed — the cut stages' code stays in the file entirely, just excluded from the cycling list.

### A real loop-wrap bug in the worklet's `Tracker`

Looping a `Tracker` at all (`loop: true`) turned out to be new territory — `Test.js` only ever played with `loop: false`, so nothing had exercised this path before. Symptom: whatever was still sounding at the tail of the last bar kept ringing straight through the loop's seam into the first bars of the next pass, instead of cutting cleanly. Root cause, found by checking the position/segment/bar math numerically (it was correct) rather than guessing: `Tracker.active[]` — "a bar with nothing new in it doesn't mean silence, it means whatever was already playing keeps playing" — is deliberately never cleared between bars, but nothing ever cleared it specifically at the loop wrap either, so a note active at the end of the range kept being treated as still-active once the playhead wrapped back to bar 0. Fixed by tracking which full pass (`cycle = floor(position / totalDuration)`) the playhead is on and clearing `active` the instant that number changes — same idea `play()`/`stop()` already use, just triggered automatically on each wrap instead of only on an explicit call. (A further, smaller issue was noticed at the very end of the loop after this fix and set aside — "something is off at the end... but forget it, it was just to prove the point" — not investigated further this session.)

### The `Analyzer` idea, and why it stayed a design discussion

Design for a source-agnostic level/spectrum `Analyzer` — a class fed samples one at a time via `process(sample)`, exposing `level` (0–1) for a level meter or `bands` (an array of 0–1 values) for a spectrum view, with zero knowledge of whether those samples came from the mixed audio output or a microphone — was worked out but not built. Level needs nothing but a streaming RMS/peak with one-pole smoothing, O(1) state, trivial on an MCU. Bands were weighed between a classic buffered FFT (needs the whole block buffered plus real/imaginary scratch space before producing anything, and a visible CPU spike every N samples) and the Goertzel algorithm (computes one target frequency's magnitude incrementally, 2 floats of state per band, genuinely one-sample-at-a-time); Goertzel was judged the better MCU fit for a handful of visualizer bands (8–32), losing only against a from-scratch few-hundred-bin spectrograph, which isn't the goal here. Decided late in the session not to build or prove the `Analyzer` in the JS simulation at all — doing that would have required the host side to run its own shadow copy of the entire render stack purely for analysis, which turned out to expose a real, pre-existing correctness bug worth fixing on its own (below) but wasn't worth chasing further just to validate an `Analyzer` design; it'll be built and proven directly on the MCU instead.

### The real bug underneath: the audio engine's time wasn't self-contained

Chasing whether the render path could safely run on both the worklet and a hypothetical host-side shadow copy surfaced a genuine, pre-existing bug, independent of anything DemoScene-specific: `Filter.process()` computed its per-sample coefficient from `cutoff / sampleRate` — a baked-in assumption that each call is exactly `1/sampleRate` seconds after the last, using the Web Audio API's global `sampleRate` directly inside the class. A targeted search found the same mistake twice more: the synth carrier's own phase accumulator (`this.phase += frequency / sampleRate`) and `SoundEvent`'s raw-sample position advance (`samplePosition += rate`, with a comment admitting it should scale by real elapsed time and not doing so) — three instances of code assuming a fixed call cadence it was never actually told was true.

Several wrong turns followed before landing on the real fix, each one corrected directly:
- First attempt threaded an explicit `dt` parameter through every render signature (`Filter.process(input, cutoff, dt)`, `Sound.render(offset, dt)`, etc.) — rejected outright: the project already has `clock.delta`, and a second, parallel time-step concept was unnecessary complexity, not a fix.
- Second attempt tried reading `clock.delta` directly everywhere instead — but `clock.update()` in the worklet only runs once per `process()` callback (once per ~128-sample block), not once per individual sample, so `clock.delta` is block-granularity; feeding that into a recursive per-sample filter would simply trade one wrong assumption for another.
- Investigated whether `performance.now()` could give the audio side finer resolution than the block-frozen `currentTime` global — it isn't available at all inside `AudioWorkletGlobalScope` (a deliberately minimal scope, unlike a normal `Worker`), so that path was closed. Separately, but for the same underlying reason (needing real sub-millisecond resolution), the **host**-side `Clock.update()` was found to genuinely have this exact bug today — it used `Date.now()`, an integer millisecond with no fractional part at all, where `performance.now()` (available on the host) returns a true sub-millisecond float. Fixed on its own merit, independent of the audio-side chase: `core/system.js`'s `Clock.update()` now reads `performance.now() / 1000`.
- Floated a `SYSTIME()` abstraction (a per-platform "give me the current high-resolution time" function, with the audio side faking per-sample resolution within a frozen block via a 0–127 counter) driven through the existing `system.loop()` — corrected as a real conceptual error, not a style objection: `system.loop()` (buttons, game state, `pixels`) and the audio render path are different loops entirely, driven by different callers (an animation frame vs. an I²S-style buffer-fill request), and conflating them was the actual mistake, not the lack of a named function.
- Proposed introducing a dedicated `AudioClock` class, including renaming the worklet's existing local `System`/`Clock` to make the distinction explicit — rejected on the no-renaming-no-removing rule; whatever existed already needed to stay, only new, additional things could be introduced.
- Clarified where audio rendering actually happens on each side: the worklet-side callback produces real output: the host side was going to need the identical render math too, for the `Analyzer`, except the result would never reach real speakers — both sides needed to run the same thing, just with different endings.

The design that actually stuck, arrived at last: `audio.render()` takes no parameters at all and fills `audio.buffer` (a plain array, already a member, not passed in or returned) in place, advancing a plain `audio.timestamp` field by one sample's duration after every sample it writes — a flat counter, not a clock class, correct as long as the buffer-fill callback is never missed or delayed, which the platform already guarantees by contract. No separate `AudioClock` class, no `dt`, no `offset` parameter anywhere. Every render function (`Sound.render`, `Filter.process`, `LFO.render`, the worklet's `Tracker.render`, `SoundEvent.render`) was stripped back to taking no time-related parameters at all, reading `this.audio.timestamp` (or `this.tracker.audio.timestamp`) directly instead of `this.audio.system.clock.time + offset`; `process()` itself simplified to a bare loop calling `this.render()` once per sample, with all offset math gone. Once every render call really is guaranteed to be exactly `1/sampleRate` apart again (true now, structurally, not assumed), `Filter`'s and the carrier phase's original `/sampleRate` formulas turned out to already be correct and were left as they were — the bug was never really in that math, it was in what the rest of the engine let call it, and under what assumptions.
