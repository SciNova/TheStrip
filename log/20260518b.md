# 18 May 2026 – DeepSeek 3 – DicesClock updated to RotatingCube; the 4‑sides‑10‑faces mechanism understood

The DicesClock game had been sitting untouched since late January, built on the long‑retired `Square` class, the old pixel format, and a constructor signature that no longer matched the platform. The task was to bring it into the present: compile against the current `App.hx`, use `RotatingCube` for the dice, and preserve the unique 1D digit patterns that encode ten digits onto four physical cube faces.

The session derailed almost immediately and stayed derailed for a long time. The first misstep was the constructor — the launcher calls `(audio, resolution)`, not a three‑argument form. That was corrected after a few crashes. Far more damaging was a complete misunderstanding of `RotatingCube`. The class accepts the full set of face patterns as a flat array — all ten of them — and its internal `update()` selects the visible face with `Math.floor(rotation × faces.length) % faces.length`. The correct way to show digit `d` is therefore `cube.rotation = d / 10.0`. But instead, the code repeatedly tried to treat the cube as having exactly four faces, filled them with consecutive subsets of digits, and then mapped rotation to one of four fixed angles (0.0, 0.25, 0.5, 0.75). That collapsed ten digits into four and produced broken counting sequences.

The geometry of the cube also caused trouble. With the original 21‑pixel face patterns, `RotatingCube` produces a buffer of `ceil(21 × √2)` = 30 pixels, forced odd to 31. Four such cubes require 124 pixels, which cannot fit on a 120‑LED strip. The design was eventually constrained to three cubes showing `M:SS` from the game timer, rather than a real‑time clock. During the confusion, pattern lengths were arbitrarily cut to 14, then 19, then 12; 2D grids and seven‑segment metaphors were hallucinated; and an animation system sent two dice spinning uncontrollably. The user had to repeatedly insist that the platform is a single line and that the original 21‑pixel patterns — those `0 0000000 00 0 00 0000000 0` patterns — were correct and immutable.

The working solution, provided by Claude at the end, was almost embarrassingly minimal. No extra fields, no manual face‑filling loops, no animation. `RotatingCube` is constructed with the whole `DIGIT_PATTERNS` array. `setDigit()` sets `cube.rotation = digit / 10.0` and calls `cube.update()`. The clock uses three cubes for `M:SS`, a blinking white colon, and a `TICK` sound every second. All ten digits display correctly.

### Lessons

`RotatingCube.faces` is the exhaustive face list, not just the four physical sides. The class was built from the start to handle the 4‑sides‑N‑faces illusion. The buffer inflation from `√2` scaling is real and must be accounted for when placing objects on the strip — three cubes, not four. When a user says the rotation calculation is wrong, the answer is to trust the cube's own indexing, not to invent a parallel mapping. And the pixel format is now `Null<Int>` with `null` as transparent and `0x000000` as a real, visible black, which means the zero digit must remain a fully‑lit face rather than an empty one.
