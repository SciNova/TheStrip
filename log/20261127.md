# 27 Nov 2026 – Claude Sonnet 5 – Audio engine flattened into core/, js/ renamed to browser/, a Node runtime added, audio.js/graphics.js/system.js all split into per-class files, and the three barrels deleted

### Why: abandoning live screen/audio capture for offline rendering

The session's actual goal was a TikTok video of Race, which led into trying to record gameplay with audio on Android. We confirmed two hard platform limits rather than bugs: `AudioContext.destination` is not a real OS media session, so Android's screen recorder and Bluetooth routing never see it; and `getDisplayMedia`/`MediaRecorder` are simply unimplemented on Android Chrome and Firefox (confirmed via caniuse and the Chromium intent threads), so in-browser screen capture isn't possible there at all. We abandoned live capture entirely in favor of offline, deterministic rendering: record only button presses and timestamps, then replay them later through a non-realtime engine that renders video frames (headless browser) and audio samples (plain synchronous render) in lockstep. That replay only works if the audio engine can run identically outside a browser tab — which meant the engine could no longer assume `AudioWorklet`, `AudioContext`, or `fetch` existed.

### core/ vs browser/ vs node/

We separated "split" classes (anything tied to `postMessage`, the AudioWorklet thread, or a DOM/WebAudio API) from "portable" classes (pure data and math, usable unchanged in a browser tab, the worklet thread, or Node). The rule we kept returning to: cross the environment boundary with exactly one duck-typed seam per concern — a plain field defaulted to `null` on the base class, assigned a real function by whichever environment constructs things — rather than parallel subclass hierarchies. Three such seams exist now: `System.load(path)` (fetch in the browser, `fs.readFile` in Node), `Clock.now()` (`performance.now()/1000` in both, but assigned rather than hardcoded), and `Sample.system` (routes `Sample.load` through whichever `system.load` is live). `js/` was renamed to `browser/` to name what it actually is; `node/audio.mjs` is new, wiring those same three seams to Node's `fs`/`performance` so the identical `core/audio.js` engine runs there untouched.

Consolidating under that rule removed real duplication: `Sound`/`LFO`/`Filter` moved out of the worklet file into `core/audio.js` (now reading `this.audio.sampleRate` instead of a bare worklet-global `sampleRate`); `Tracker` moved into its own `core/tracker.js` since it's pure bookkeeping with no environment dependency; `browser/audio.js`'s own duplicate `Synth`/`Sampler`/`Sample`/`Clock` classes were deleted outright in favor of importing the real ones. `Sample` itself went from two environment-specific subclasses each overriding `static load` down to one class, with a hand-rolled `decodeWav` (chunk-walking `DataView` parser) verified byte/frame-identical against both Python's `wave` module and `AudioContext.decodeAudioData`.

### MODFormat, ABCFormat, JSONFormat: dropping `load()` as a class responsibility

`MODFormat`/`ABCFormat` both carried their own `load(path)`/`_readBinary`/`_readText` methods, each independently deciding how to fetch a file — a second, redundant environment seam alongside `system.load`. We removed both entirely; a format class now only ever takes an already-loaded buffer or string in its constructor, and the caller is responsible for getting bytes via `system.load(path)` first. This surfaced a real layering violation along the way: `core/mod.js` was importing `Sample` from `browser/audio.js` instead of `core/audio.js`, and separately constructing a throwaway `Sample` with a name string that got immediately overwritten — both fixed as part of the same pass. `core/mod.js` also merged its `_readSamples`/`_readSampleData` pair into one parameter-less `readSamples()` instance method, and started reading a sample's volume directly from the buffer at its real header offset instead of through a pre-built intermediate array. A later, smaller pass found the same pattern one more time: `core/json.js`'s `JSONFormat.load()` still branched on `fetch` vs `fs` internally; it lost that method the same way, with no behavior change since nothing in the codebase called it yet.

### Splitting audio.js and graphics.js into one class per file

Once the engine was properly flattened, both `core/audio.js` and `core/graphics.js` still carried several unrelated classes and constant tables in a single file each. We split both into one file per class/concern — `core/audio/` gained `Note`, `Waveform`, `LFODestination`, `LFO`, `Filter`, `Sound`, `Audio`, `Sample`, `SystemSound`, `SoundEvent`, `Track`, `Tracker`, `ModFormat`, `ABCFormat`, and `JSONFormat`; `core/graphics/` gained `Alignment`, `EdgeMode`, `Shape`, `Shape2D`, `SquareView`, `Square`, `Square2D`, `Camera`, `BasePlayer`, `BasePlayer1D`, `BasePlayer2D`, `BaseWorld`, `World`, `World2D`, `WidgetState`, `Widget`, and `ProgressBar` — with `core/audio.js` and `core/graphics.js` themselves reduced to pure re-export barrels. Every existing game and app still imports from the two barrel files unchanged; the explicit intent is that each game will eventually import only the specific classes it actually uses, once there's a real reason to, rather than rewriting ~40 import sites speculatively today.

Every new and touched file was syntax-checked with `node --check`, and the split was functionally verified rather than just assumed safe: `node/audio.mjs` loading a real `.mod` file and a real `.wav` sample through the new `core/audio/ModFormat.js`/`Sample.js` reproduced the exact same tempo, segment count, sample count, duration, and frame count as before the split; `Shape.render` and `ProgressBar.render` were run against a stub game object and produced correct pixel output; `JSONFormat.stringify`/`parse` round-tripped a constructed `Track` back to an identical structure.

### `Colors` renamed to `Color`, and `Command` rebuilt as a real class

Asked why `core/system.js`'s color table was named `Colors` (plural) when every other enum-shaped table in the file — `Command`, `GameId`, `Waveform`, `EdgeMode`, `WidgetState` — is singular, we found no principled reason in the project's own history (a 31 Jan 2026 dev-log entry records the enum-to-plain-object rename but never explains the pluralization); it read as leftover inconsistency, not a rule, so we renamed it `Color` across all 41 files that referenced it.

Moving `GAME_COMMANDS`/`isGameCommand` onto `Command` itself went through two false starts worth recording. The first pass built `Command` as a frozen object literal via an invented intermediate name, `CommandValues`, purely to let `GAME_COMMANDS` reference the object's own fields before freezing it — flagged immediately as pointless, since `const Command` can be mutated before freezing with no second name needed at all. The second correction was sharper: told flatly "it needs to be a class," we rebuilt `Command` as an actual `class` with `static` fields instead of a frozen object, matching the convention every other such file in the codebase already follows (`Note`, `MODFormat`, ...) — object-literal-plus-freeze was never the house style for these, and `Command` had only been one because of how it happened to be written originally.

### Splitting the rest of `core/system.js`

Once `Command`/`Color` were clean, the same one-class-per-file treatment already applied to `audio.js`/`graphics.js` was extended to everything else `system.js` still carried: `Clock.js`, `DebouncedPin.js`, `Button.js` (`ButtonState`/`ButtonEvent`/`Button`), `Pad.js`, `WiredPad.js`, `Encoder.js` (`EncoderState`/`EncoderEvent`/`Encoder`), `Strip.js`, `Menu.js`, `System.js` (`SystemState`/`System`), `Game.js` (`GameState`/`Game`, with `GameId` folded in alongside it since nothing else used it). `Pad`/`WiredPad` were first put in `Button.js` by mistake — `WiredPad` only builds `Button` instances, it isn't one — and corrected into their own files once flagged. The three free color-conversion functions (`balanceColors`, `correctGamma`, `hsvToRgb`) moved onto `System` as `static` methods at explicit request, despite having no real conceptual tie to `System`'s actual job (pad/menu/game-state wiring) — a case of following a direct instruction over our own architectural preference, with the four external call sites (`core/graphics/Shape.js`, `drafts/Test/Test.js`, `apps/ColorLight/ColorLight.js`, `apps/DemoScene/DemoScene.js`) updated to match. `system.js` itself became a pure re-export barrel through all of this, so none of the ~80 importing app/draft files needed to change yet.

### `browser/Console.js` and `browser/hardware.js` split the same way

`StripView` and `StripView3D` moved out of `Console.js` into their own files; `StripView3D` kept its logo-floor-texture helpers and constants, but as `static` members of the class itself rather than module-level consts/functions, once asked specifically to move them in. `Console.js`'s own remaining module-level state (`ARROW_DIRECTION_INDEX`, `panelSvgCache`) moved onto the class too — a `static` field for the constant lookup table, a per-instance field for the cache, since a cache shared across every `Console` instance was never actually the intent.

`hardware.js` lost `WiredPadView` (to its own file, with `Pad`/`WiredPad` further split out of that into `core/Pad.js`/`core/WiredPad.js`), and its remaining `PcbPanel`/`PcbPanelABCD`/`PcbPanelABC`/`PcbPanelF`/`PcbPanelUD`/`PcbPanelLR`/`PcbPanelLRF`/`PcbPanelUDF`/`PcbPanelLRUDFF` classes were renamed to drop the redundant `Pcb` prefix (`Panel`, `PanelABCD`, ...) — `PcbPanelModel`, the physical-model enum, was deliberately left alone as a distinct concept. Once only the `Panel*` classes remained, the file itself was renamed `hardware.js` → `Panel.js`.

### Migrating every game off the three barrels, then deleting them

With `Slots.js` done first as a trial (one class per line, each from its real file, confirmed importable and syntax-clean), the same treatment was mechanically applied to the remaining 44 app/draft files via a small Python script driven by a name→file map built from every real `export` statement under `core/`: each barrel import line (`from '../../core/system.js'` etc.) expanded into one `import { X } from '...'` line per class. Every file was syntax-checked, then functionally imported end-to-end under Node (with `FontFace`/`document`/`THREE`/`AudioContext`/`ResizeObserver` stubbed) to catch path mistakes a syntax check alone wouldn't — all 45 passed clean on the first full run.

That left only 9 files anywhere in the repo still importing from a barrel: `browser/StripView.js`, `StripView3D.js`, `WiredPadView.js`, `Panel.js`, `audio-processor.js`, `Console.js`, `audio.js`, `index.html`, and `node/audio.mjs`. Each was switched to direct per-class imports the same way, confirmed with a fresh repo-wide grep that zero references to `core/system.js`/`core/audio.js`/`core/graphics.js` remained anywhere, and only then were the three barrel files deleted outright. Verified afterward: `node/audio.mjs` still loads a real `.mod` and `.wav` with identical tempo/segment/sample/frame values as every earlier check in this log; every browser-side file still imports cleanly once its real-environment-only globals are stubbed, including `audio-processor.js`, whose one failure (`AudioWorkletProcessor is not defined`) was confirmed to be the pre-existing, expected limit of testing a worklet script outside a real worklet thread, not an import-path regression — stubbing that one global too let it resolve clean as well.
