# 27 Nov 2026 – Claude Sonnet 5 – Audio engine flattened into core/, js/ renamed to browser/, a Node runtime added, audio.js/graphics.js/system.js all split into per-class files, system/audio/graphics barrels deleted, a portability experiment translating core/ classes into C++ and Python, and the WiredConsole/WiredPad hardware model extracted out of the browser layer with the page restructured into a setup/loop Application

### Why: abandoning live screen/audio capture for offline rendering

The session's actual goal was a TikTok video of Race, which led into trying to record gameplay with audio on Android. We confirmed two hard platform limits rather than bugs: `AudioContext.destination` is not a real OS media session, so Android's screen recorder and Bluetooth routing never see it; and `getDisplayMedia`/`MediaRecorder` are simply unimplemented on Android Chrome and Firefox (confirmed via caniuse and the Chromium intent threads), so in-browser screen capture isn't possible there at all. We abandoned live capture entirely in favor of offline, deterministic rendering: record only button presses and timestamps, then replay them later through a non-realtime engine that renders video frames (headless browser) and audio samples (plain synchronous render) in lockstep. That replay only works if the audio engine can run identically outside a browser tab — which meant the engine could no longer assume `AudioWorklet`, `AudioContext`, or `fetch` existed.

### core/ vs browser/ vs node/

We separated "split" classes (anything tied to `postMessage`, the AudioWorklet thread, or a DOM/WebAudio API) from "portable" classes (pure data and math, usable unchanged in a browser tab, the worklet thread, or Node). The rule we kept returning to: cross the environment boundary with exactly one duck-typed seam per concern — a plain field defaulted to `null` on the base class, assigned a real function by whichever environment constructs things — rather than parallel subclass hierarchies. Three such seams exist now: `System.load(path)` (fetch in the browser, `fs.readFile` in Node), `Clock.now()` (`performance.now()/1000` in both, but assigned rather than hardcoded), and `Sample.system` (routes `Sample.load` through whichever `system.load` is live). `js/` was renamed to `browser/` to name what it actually is; `node/audio.mjs` is new, wiring those same three seams to Node's `fs`/`performance` so the identical `core/audio.js` engine runs there untouched.

Consolidating under that rule removed real duplication: `Sound`/`LFO`/`Filter` moved out of the worklet file into `core/audio.js` (now reading `this.audio.sampleRate` instead of a bare worklet-global `sampleRate`); `Tracker` moved into its own `core/tracker.js` since it's pure bookkeeping with no environment dependency; `browser/audio.js`'s own duplicate `Synth`/`Sampler`/`Sample`/`Clock` classes were deleted outright in favor of importing the real ones. `Sample` itself went from two environment-specific subclasses each overriding `static load` down to one class, with a hand-rolled `decodeWav` (chunk-walking `DataView` parser) verified byte/frame-identical against both Python's `wave` module and `AudioContext.decodeAudioData`.

### MODFormat, ABCFormat, JSONFormat: dropping `load()` as a class responsibility

`MODFormat`/`ABCFormat` both carried their own `load(path)`/`_readBinary`/`_readText` methods, each independently deciding how to fetch a file — a second, redundant environment seam alongside `system.load`. We removed both entirely; a format class now only ever takes an already-loaded buffer or string in its constructor, and the caller is responsible for getting bytes via `system.load(path)` first. This surfaced a real layering violation along the way: `core/mod.js` was importing `Sample` from `browser/audio.js` instead of `core/audio.js`, and separately constructing a throwaway `Sample` with a name string that got immediately overwritten — both fixed as part of the same pass. `core/mod.js` also merged its `_readSamples`/`_readSampleData` pair into one parameter-less `readSamples()` instance method, and started reading a sample's volume directly from the buffer at its real header offset instead of through a pre-built intermediate array. A later, smaller pass found the same pattern one more time: `core/json.js`'s `JSONFormat.load()` still branched on `fetch` vs `fs` internally; it lost that method the same way, with no behavior change since nothing in the codebase called it yet.

### Splitting audio.js and graphics.js into one class per file

Once the engine was properly flattened, both `core/audio.js` and `core/graphics.js` still carried several unrelated classes and constant tables in a single file each. We split both into one file per class/concern — `core/audio/` gained `Note`, `Waveform`, `LFODestination`, `LFO`, `Filter`, `Sound`, `Audio`, `Sample`, `SystemSound`, `SoundEvent`, `Track`, `Tracker`, `ModFormat`, `ABCFormat`, and `JSONFormat`; `core/graphics/` gained `Alignment`, `EdgeMode`, `Shape`, `Shape2D`, `SquareView`, `Square`, `Square2D`, `Camera`, `BasePlayer`, `BasePlayer1D`, `BasePlayer2D`, `BaseWorld`, `World`, `World2D`, `WidgetState`, `Widget`, and `ProgressBar` — with `core/audio.js` and `core/graphics.js` themselves reduced to pure re-export barrels. Every existing game and app still imports from the two barrel files unchanged; the explicit intent is that each game will eventually import only the specific classes it actually uses, once there's a real reason to, rather than rewriting ~40 import sites speculatively today.

Every new and touched file was syntax-checked with `node --check`, and the split was functionally verified rather than just assumed safe: `node/audio.mjs` loading a real `.mod` file and a real `.wav` sample through the new `core/audio/ModFormat.js`/`Sample.js` reproduced the exact same tempo, segment count, sample count, duration, and frame count as before the split; `Shape.render` and `ProgressBar.render` were run against a stub game object and produced correct pixel output; `JSONFormat.stringify`/`parse` round-tripped a constructed `Track` back to an identical structure.

### `Colors` renamed to `Color`, and `Command` rebuilt as a real class

Asked why `core/system.js`'s color table was named `Colors` (plural) when every other enum-shaped table in the file — `Command`, `GameId`, `Waveform`, `EdgeMode`, `WidgetState` — is singular, we found no principled reason in the project's own history (a 31 Jan 2026 dev-log entry records the enum-to-plain-object rename but never explains the pluralization); it read as leftover inconsistency, not a rule, so we renamed it `Color` across all 41 files that referenced it.

Moving `GAME_COMMANDS`/`isGameCommand` onto `Command` itself went through two false starts worth recording. The first pass built `Command` as a frozen object literal via an invented intermediate name, `CommandValues`, purely to let `GAME_COMMANDS` reference the object's own fields before freezing it — flagged immediately as pointless, since `const Command` can be mutated before freezing with no second name needed at all. The second correction was sharper: told flatly "it needs to be a class," we rebuilt `Command` as an actual `class` with `static` fields instead of a frozen object, matching the convention every other such file in the codebase already follows (`Note`, `MODFormat`, ...) — object-literal-plus-freeze was never the house style for these, and `Command` had only been one because of how it happened to be written originally.

### Splitting the rest of `core/system.js`

Once `Command`/`Color` were clean, the same one-class-per-file treatment already applied to `audio.js`/`graphics.js` was extended to everything else `system.js` still carried: `Clock.js`, `DebouncedPin.js`, `Button.js` (`ButtonState`/`ButtonEvent`/`Button`), `Pad.js`, `WiredPad.js`, `Encoder.js` (`EncoderState`/`EncoderEvent`/`Encoder`), `Strip.js`, `Menu.js`, `System.js` (`SystemState`/`System`), `Game.js` (`GameState`/`Game`, with `GameId` folded in alongside it since nothing else used it). `Pad`/`WiredPad` were first put in `Button.js` by mistake — `WiredPad` only builds `Button` instances, it isn't one — and corrected into their own files once flagged. The three free color-conversion functions (`balanceColors`, `correctGamma`, `hsvToRgb`) moved onto `System` as `static` methods at explicit request, despite having no real conceptual tie to `System`'s actual job (pad/menu/game-state wiring) — a case of following a direct instruction over our own architectural preference, with the four external call sites (`core/graphics/Shape.js`, `drafts/Test/Test.js`, `apps/ColorLight/ColorLight.js`, `apps/DemoScene/DemoScene.js`) updated to match. `system.js` itself became a pure re-export barrel through all of this, so none of the ~80 importing app/draft files needed to change yet.

### `browser/Console.js` and `browser/hardware.js` split the same way

`StripView` and `StripView3D` moved out of `Console.js` into their own files; `StripView3D` kept its logo-floor-texture helpers and constants, but as `static` members of the class itself rather than module-level consts/functions, once asked specifically to move them in. `Console.js`'s own remaining module-level state (`ARROW_DIRECTION_INDEX`, `panelSvgCache`) moved onto the class too — a `static` field for the constant lookup table, a per-instance field for the cache, since a cache shared across every `Console` instance was never actually the intent.

`hardware.js` lost `WiredPadView` (to its own file, with `Pad`/`WiredPad` further split out of that into `core/Pad.js`/`core/WiredPad.js`), and its remaining `PcbPanel`/`PcbPanelABCD`/`PcbPanelABC`/`PcbPanelF`/`PcbPanelUD`/`PcbPanelLR`/`PcbPanelLRF`/`PcbPanelUDF`/`PcbPanelLRUDFF` classes were renamed to drop the redundant `Pcb` prefix (`Panel`, `PanelABCD`, ...) — `PcbPanelModel`, the physical-model enum, was deliberately left alone as a distinct concept. Once only the `Panel*` classes remained, the file itself was renamed `hardware.js` → `Panel.js`.

### Migrating every game off the three barrels, then deleting them

With `Slots.js` done first as a trial (one class per line, each from its real file, confirmed importable and syntax-clean), the same treatment was mechanically applied to the remaining 44 app/draft files via a small Python script driven by a name→file map built from every real `export` statement under `core/`: each barrel import line (`from '../../core/system.js'` etc.) expanded into one `import { X } from '...'` line per class. Every file was syntax-checked, then functionally imported end-to-end under Node (with `FontFace`/`document`/`THREE`/`AudioContext`/`ResizeObserver` stubbed) to catch path mistakes a syntax check alone wouldn't — all 45 passed clean on the first full run.

That left only 9 files anywhere in the repo still importing from a barrel: `browser/StripView.js`, `StripView3D.js`, `WiredPadView.js`, `Panel.js`, `audio-processor.js`, `Console.js`, `audio.js`, `index.html`, and `node/audio.mjs`. Each was switched to direct per-class imports the same way, confirmed with a fresh repo-wide grep that zero references to `core/system.js`/`core/audio.js`/`core/graphics.js` remained anywhere, and only then were the three barrel files deleted outright. Verified afterward: `node/audio.mjs` still loads a real `.mod` and `.wav` with identical tempo/segment/sample/frame values as every earlier check in this log; every browser-side file still imports cleanly once its real-environment-only globals are stubbed, including `audio-processor.js`, whose one failure (`AudioWorkletProcessor is not defined`) was confirmed to be the pre-existing, expected limit of testing a worklet script outside a real worklet thread, not an import-path regression — stubbing that one global too let it resolve clean as well.

### A portability experiment: translating core/ classes line-per-line into C++ and Python

With the barrels gone and one class per file, the next question was different: is the resulting JS actually *language-agnostic* — written at a level where it could be C++ or Python with only syntax changed — or does it secretly lean on JS-only tricks? The test: translate each core class into a `.h` and a `.py` file, line-per-line, no imports, nothing that needs to build, just the class bodies. Wherever the translation stopped being mechanical, that was a real finding: either a genuine language gap to solve once, or a spot where the JS itself was quietly relying on a JS-only trick and should be fixed instead of ported around.

#### Recurring pattern: null has no home in a typed enum or a typed array

The single most common snag: JS routinely uses `null`/`undefined` as an implicit extra value outside an enum's or array's declared domain — `Button.process()` returning `null` for "no event," `Shape.pixels` using `null` to mean "no pixel here." A C++ `enum class` has no such out-of-band value, and a C array has no slot for "nothing" without a sentinel or a parallel bool. The fix that held up: don't invent a fake enum member (`ButtonEvent.NONE` — tried first, rejected, since it doesn't exist in the JS/Python version and breaks the three-way equivalence) and don't reach for `std::optional` (ruled out, no STL anywhere in this exercise). Instead, `Button`/`Encoder` return a plain `bool` plus an out-parameter for the real event — native to C, no fake values, no library. The pixel-array version of the same problem (`Shape.pixels`, `SquareView`'s face patterns) is still open.

#### Recurring pattern: a dict used to glue facts together, instead of fields on one object

`Command.GAME_COMMANDS` was a JS array checked only with `.includes()` — translating that needed an invented `GAME_COMMANDS_COUNT` for C++, which was the real tell: the array never should have existed. `Command.isGameCommand()` became a plain chain of equality checks instead, and the (also unused, dead) `Command.NONE` was deleted outright once grep confirmed nothing referenced it.

The same shape showed up worse in `WiredPad`: `this.buttons` was a `{A: ..., B: ..., ...}` object keyed by button name, and `WiredPadView` kept three more parallel dictionaries (`COMMANDS`, `pressed`, and a reverse `PANEL_BUTTON_NAMES`) all keyed by that same string — the name existed purely to say "these four facts describe the same button," not because anything needed dynamic string lookup. Fixed by giving `Button` a set of integer identity constants (`Button.A = 0`, `Button.B = 1`, ...) and turning every one of those dictionaries into a plain array indexed by those constants — explicit array literals, never loop-constructed (no invented length constant either; a first attempt at `Button.COUNT` for sizing was rejected the same way `GAME_COMMANDS_COUNT` was). The same pattern reappears, unresolved, in `core/audio/`: `SystemSound[name.toUpperCase()]` and `JSONFormat`'s reverse name-search over it, plus `SoundEvent`'s `Note[this.note]` lookup when a note arrives as a string instead of its numeric constant.

#### A JS trick with no C++/Python equivalent at all: a constructor returning a different object

`MODFormat` and `ABCFormat` both end their constructor with `return track;` — JS quietly allows a constructor to replace `this` with a different object, so `new MODFormat(buffer)` never actually produces a `MODFormat`, it produces a `Track`. Neither C++ nor Python constructors can do this at all. These two classes are really disguised factory functions and will need to become real `static` factory methods before porting makes sense — parked rather than worked around.

#### Other findings, parked rather than patched over

- **`Game.buildStage`**: `playLevel()` used to do `if (this.buildStage) this.buildStage();`, leaning on JS treating a missing method as falsy. Fixed instead of ported around: `Game` now defines a no-op `buildStage()`, every subclass override still wins normally, and `playLevel()` calls it unconditionally — the JS got cleaner, not just more portable.
- **`Game.sounds` / `System.sounds`**: both started as `this.sounds = []`, relying on JS arrays silently growing when assigned at an out-of-range index — a real latent bug, since `sounds[this.freeChannel()] = sound` would corrupt memory in C++ and raise in Python. Fixed in the JS itself to `new Array(Audio.CHANNELS).fill(null)`, matching the pre-sized version that `browser/audio-processor.js` already had separately.
- **`trackers`** (on both `Game` and `System`): genuinely unbounded in principle, but can't exceed `Audio.CHANNELS` (10) in practice. Capping it needs more than a fixed-size array, though — nothing currently frees a tracker's slot once added, even after it stops, so a naive fixed array would fill up permanently after the first 10 trackers ever created. Needs a real slot-freeing design before it can be ported; parked.
- **`System.GAMES`**: a dictionary of actual classes keyed by numeric `GameId`, instantiated dynamically (`new GameClass(this)`) to load whichever of the ~46 games the player picked. Trivial in JS (classes are values); C++ has nothing like it without a hand-built factory-pointer table. Architecture-level, parked alongside `trackers`.
- **`SquareView.update(obj)`**: takes a plain duck-typed object rather than a typed instance, relying on structural typing to accept both `Square` and `Square2D` even though neither shares a common base exposing the fields it needs (`faces`, `invert`). Needs a real shared interface or base class in C++; Python needs no change.
- **`Filter.process(input, cutoff = this.cutoff)`**: a default argument that reads instance state — not expressible as a C++ or Python default argument in either language. Caught myself trying to silently paper over it with a C++ overload before stopping to flag it instead.
- **`core/audio/ABCFormat.js`**: a full hand-rolled ABC-notation text parser (stateful regexes, `Map`, recursive bar/voice splitting). Not a quirk to resolve — any port is a from-scratch rewrite regardless of how the other findings above are resolved.

#### Result: 23 classes proven portable, 17 not yet

Translated line-per-line into matching `.h`/`.py` pairs, no quirks beyond ordinary syntax: `Button`, `Encoder`, `DebouncedPin`, `Color`, `Command`, `Pad`, `WiredPad`, `Strip`, `Alignment`, `EdgeMode`, `WidgetState`, `Camera`, `BasePlayer`, `BasePlayer1D`, `BasePlayer2D`, `BaseWorld`, `World`, `World2D`, `Widget`, `ProgressBar`, `Note`, `Waveform`, `LFODestination`, `LFO`.

Not yet portable, each needing one of the design decisions above before translation makes sense: `Game`, `System`, `Shape`, `Shape2D`, `Square`, `Square2D`, `SquareView`, `Filter`, `Track`, `Audio`, `Sample`, `Sound`, `SoundEvent`, `SystemSound`, `ModFormat`, `ABCFormat`, `JSONFormat`.

23 against 17 was enough to answer the actual question — the point was never to finish a full C++/Python port, just to find out whether `core/` is genuinely language-agnostic. It mostly is, and the handful of places it isn't are now a known, named list instead of a vague feeling.

#### Housekeeping: folder cleanup

Two stray monolithic leftover files — `core/graphics.h`/`core/graphics.py`/`core/system.h`/`core/system.py`, old barrel-style whole-file translations unrelated to today's per-class exercise — were found and deleted. `core/tunes/` (five `.abc` files, confirmed unreferenced anywhere in the codebase) was renamed to `mods/` and moved to the repo root. The new `.h` files moved to `cpp/core/` (with `audio/`/`graphics/` subfolders preserved) and the `.py` files to `python/core/`, leaving `core/` holding only the real JS source again.

### Extracting WiredConsole/WiredPad out of the browser layer, and giving the page a setup/loop structure

Picking back up in the same session: the portability exercise above left one piece of the mental model nagging - `WiredPad`/`System` live in `core/`, but all of the actual button-reading, event-dispatch, and panel/view wiring lived in `browser/WiredPadView.js` and `browser/Console.js`. That's backwards for a thing meant to run on an MCU too: on real hardware the equivalent is an Arduino sketch's `setup()`/`loop()` - `setup()` configures pins once, `loop()` reads them and drives the rest every tick. The browser should only differ at the one point where it genuinely has to: how raw input *arrives* (reactive DOM events vs. polled `digitalRead`), never in how it's processed afterward.

#### WiredPad.loop() moved from the view into core, replacing lookup arrays with explicit per-button code

`WiredPadView.loop()` held the entire button→`Command` translation (a `COMMANDS` lookup array keyed by button id, iterated in a loop). Both problems got fixed at once: the whole method moved into `WiredPad` itself (core, not browser), and the lookup array was replaced with one explicit block per button (`this.buttons[Button.A].process(...)`, `if (event === ButtonEvent.PRESS) ...`) - matching the project's established "no array as a stand-in for an identity" rule. `Button.A`/`Button.B`/etc as integer identity constants (added in the earlier session) made this direct indexing possible without string keys.

#### The repeated wrong turns on where raw input state should live

Getting the physical-input plumbing right took several real misses, each one a small lesson:

- First pass had `WiredPad.loop()` self-referentially deriving "is this button currently pressed" from the button's own `state` field (`state !== ButtonState.IDLE`) - works for continuing an already-started HOLD, but can never *start* a new press, since nothing external ever fed in a fresh edge.
- Tried routing every DOM event handler (`WiredPadView`, keyboard in `Console`) to call `button.process()` and dispatch the `Command` directly, inline, at the moment of the event - fully reactive, no loop needed at all for buttons. Rejected: this breaks HOLD detection, since nothing re-checks elapsed time while a button is held with no new DOM events in between (release would always read as a short press, no matter how long it was actually held).
- Landed on the Arduino-correct shape instead: a persistent `Input` concept holding the raw "is this physically down" boolean per button (what a `digitalRead` would return), fed by DOM handlers (reactive: `keydown`/`mousedown` set it `true`, `keyup`/`mouseup` set it `false`), and read every tick by the one real `loop()` that calls `process()` and dispatches. Both platforms run the exact same `loop()` body; only how the boolean gets set differs.
- `Input` as its own class bounced between `core/` and `browser/` twice, and bounced between holding a reference to `pads` directly vs. to the owning console, before landing on the simplest shape: no separate class at all. The two 18-item boolean arrays (`inputs`) and `loop()` both live directly on `WiredConsole` - it already owns `system` and both `pads`, so there was no real reason for a fourth object in between.
- Button→console plumbing had the same back-and-forth: a `WiredPadView.parent` field pointing at its owning `WiredConsoleView` (rejected - wrong layer, a browser view reaching into another browser view) corrected to `WiredPad.console`, a plain backreference set entirely inside `WiredConsole`'s own constructor (`new WiredPad(this, 0)`), pure core-to-core wiring with zero browser involvement.

#### Result: WiredConsole as the real "sketch" for the console hardware

`core/WiredConsole.js` now owns `system`, both `pads`, and `inputs`, and its `loop()` is the actual sketch body: update the clock first, then for every button on both pads read `inputs`, call `process()`, dispatch the resulting event to a `Command`. `WiredPad`'s constructor takes the owning `console` directly (not `system` separately) and derives `console.system` itself.

`browser/WiredPadView.js` and the renamed `browser/WiredConsoleView.js` (was `Console.js`; the class itself renamed too, for the same reason `WiredPad`/`WiredConsole` are named for the product generation - "wired" is this console's real identity, not a stand-in pattern name for a family of console types) now do nothing but DOM wiring: constructing the view, loading/rendering panel SVGs, and - the only genuinely platform-specific code left anywhere in this path - handlers that flip a boolean in `console.inputs` on `keydown`/`keyup`/`mousedown`/`mouseup`/`touchstart`/`touchend`. No button state, no event objects, no `Command` knowledge anywhere in the browser layer.

#### browser/Application.js: the page itself gets the same setup/loop shape

Applying the same lesson one level up: all of `index.html`'s inline `<script>` - every game-class import, the `GAMES` registry, constructing the console view, wiring the debug panel/menu/panel-swap/hide buttons, and the `requestAnimationFrame` frame function - was the page's own `setup()`/`loop()`, just not named or structured as one. Extracted into `browser/Application.js` as an `Application` class: `setup(resolution)` does everything `init()` used to do once, `loop()` does what the old `frame()` closure did every tick. `index.html` now only imports `Application`, registers `window.init`/`window.loadGame` as thin bridges for the page's inline `onclick` markup (which can't reach a module-scoped `const` directly), and runs one `requestAnimationFrame` loop calling `app.loop()`.

One real (positive) behavior change fell out of this for free: the old code started a brand-new `requestAnimationFrame` chain inside every call to `init()`, with no cancellation of any previous chain - so changing resolution more than once before power-on could leave multiple loops running in parallel against the same console. The new structure has exactly one persistent loop for the page's lifetime, reading `app.consoleView` fresh each tick, so that can't happen anymore.

The view-repaint throttle (capped below the display's refresh rate so the 3D view doesn't compete with the browser's audio engine for CPU/GPU) moved too, and went through the same lesson as `Input`: initially reintroduced as an `Application`-level `timestamp`/`VIEW_UPDATE_INTERVAL` pair driven by `requestAnimationFrame`'s own timestamp parameter - wrong, since nothing should exist outside `clock.timestamp`/`clock.delta` and `loop()` shouldn't take a parameter at all. Fixed by moving the throttle entirely into `WiredConsoleView.updateView()` itself, comparing `console.system.clock.timestamp` (the real, already-advancing clock) against its own `this.timestamp` field, with `VIEW_UPDATE_INTERVAL` as a `static` class constant rather than a per-instance field.

Committed as a single commit covering both the C++/Python portability experiment and this extraction work.
